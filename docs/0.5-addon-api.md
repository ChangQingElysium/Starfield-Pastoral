# StardewCraft 0.5 附属与数据包 API

本文描述 `com.stardew.craft.api.v1` 当前已经落地的入口。进入
`compatibility/public-api-v1.txt` 的类型属于稳定契约，在 0.5.x 内保持兼容；
`compatibility/experimental-api-v1.txt` 中的类型仍处于实验阶段，会按扩展平台
路线图进行收敛，不能仅因位于 `api.v1` 就视为已经冻结。实验接口的调整仍以
保留本体行为、存档和已有兼容入口为前提。

## 扩展平台设计原则

扩展能力按 StardewCraft 自身的完整游戏系统设计，不以某一个现有附属的实现方式
反推核心接口。多个真实世界附属只作为兼容性与迁移成本的回归样本，不决定 API 的边界。

每个系统优先形成三层：

1. 数据包负责可枚举、可重载的内容身份、关系、条件和布局；
2. Java 注册入口负责新实体、新算法及无法纯数据表达的运行时能力；
3. 核心运行时只消费统一身份和不可变快照，并把跨系统引用投影到内容目录。

新增入口必须默认保持旧行为：没有新定义时走原逻辑，已有 Java Provider 不改变
优先级，坏的 reload 候选原子回滚，存档中的未知命名空间数据予以保留。旧入口只有
在新路径覆盖其实际能力、已有附属具备迁移窗口且删除不会破坏世界时才进入弃用流程；
不会为了“统一”一次性改写网络、存档或所有调用者。

## 当前能力边界

已经可用：

1. 数据包可以给任意已注册物品添加同步的星露谷元数据。
2. 附属 Mod 可以注册按 `ItemStack` 动态计算的物品元数据 Provider。
3. 附属 Mod 可以注册带 `Codec` 的 Condition、Item Query 和服务端 Action 类型。
4. 剧情定义 reload 已具备原子替换、诊断、版本和内容哈希。
5. 数据包可以定义任务链，附属 Mod 可以注册带独立存档状态的任务目标类型。
6. 数据包可以新增商店、商店交互绑定、邮件、剧情和特殊订单。
7. 附属 Mod 可以注册动态商店库存、剧情触发器、客户端演出命令，以及特殊订单目标和奖励类型。
8. 数据包可以扩展机器、烹饪、合成、解锁来源、钓鱼宝箱、鱼塘、公会目标、博物馆奖励、遗失藏书、自定义晶球、兑奖奖励和矿井层宝箱。
9. 数据包可以新增带命名空间的节日日期、时段、日历、地点和地图覆盖定义；附属 Mod 可以给节日绑定复杂玩法 Handler。
10. 数据包可以扩展蚯蚓点、采集区、采石场、骷髅矿井奖励、矿层主题、怪物刷怪表、地点、传送目标、精通奖励与职业元数据。
11. 作物、树、动物、建筑和装备支持同步 Data Map；附属 Mod 可以注册动态 Provider、托管动物类型、动物日结、繁殖与松露替换规则、武器技能、职业效果和矿井怪物 Handler。
12. 本体 57 个静态商店和 16 条特殊订单已经迁入同一套公开数据格式。
13. NPC 支持社交/送礼规则、友情奖励、实体解析、客户端展示 DTO，以及礼物确认与前后钩子。
14. 数据包或附属 Mod 可以定义完整农场布局；选择、创建、存档、所有权转移、
    边界、传送、洞穴、采集区和初始化结构使用同一个布局描述。
15. 地图数据包可以声明命名空间世界锚点；NPC 命名日程点、Portal 目标和节日
    场地已经使用同一目录。
16. 数据包和 Java 附属可以向任意命名空间建筑目录增加蓝图；Robin 与 Wizard
    已迁移到同一目录和服务端权威购买事务。

明确边界：

1. 数据定义不能注册新物品、方块、实体、菜单、声音或地图结构；这些仍需要 Mod 和资源包。
2. 地点与传送定义只描述已有区域和目的地，不会移动预生成室内或自动放置传送触发器。
3. 核心技能和职业拥有状态仍使用固定枚举与旧数字存档；0.5.x 不支持运行时新增第六种技能或任意新职业槽位。
4. 旧邮件数组和旧剧情命令继续兼容；新内容应使用命名空间定义和公共 Condition/Action。

0.5 提供的是稳定的内容接口和已迁移业务链，不承诺把世界生成、GUI 协议和核心存档模型都变成数据文件。

## 登录、reload 与客户端展示

服务端在玩家登录和 `/reload` 完成后都通过同一 NeoForge 同步事件发送最新快照。注册表文档单份上限为 4 MiB，整个快照上限为 16 MiB；声明长度超限或正文截断会在分配目标数组前被拒绝。

邮件收藏只接收 `mailId/textKey`，不接收奖励 Action。节日日历只接收服务端判定后的可用 ID。JEI 会用展示用 DTO 刷新钓鱼、既有工匠机器、合成、商店和晶球条目；断线时这些快照会清空，不会带到下一个服务器。JEI 的分类注册只发生在它启动时，因此 `/reload` 可刷新已存在分类的条目，但不能在运行中新建一种全新的机器分类。

建筑目录请求增加稳定蓝图 ID 和服务端 revision 后，0.5 网络协议版本为 `5`；
客户端与服务端版本不同时会拒绝连接，不尝试混合解码。

## 地点与世界锚点

逻辑地点继续使用 `data/<namespace>/locations/<path>.json` 定义有维度边界和 alias
的区域，并可声明 `parent`、本地化展示、图标、命名空间标签和环境属性。运行时
统一通过 `StardewLocations` 查询，钓鱼地点键、节日地点验证和遗物点上下文已经
接入这个目录，并消费同一个不可变 revision。定义、父子继承结果、完整 ID/alias
索引、室内区域和
客户端同步 JSON 一次发布；失败 reload 保留上一整套视图，不会出现新父级配旧子级
或新地点配旧 alias。

一个地点不是单个长方体时，可以用一个或多个共享区域细化它：

```text
data/myaddon/regions/orchard_shape.json
```

```json
{
  "dimension": "stardewcraft:stardew_valley",
  "location": "myaddon:orchard",
  "include": [
    {"min": [100, 50, -40], "max": [130, 90, -10]},
    {"min": [131, 50, -25], "max": [160, 90, 5]}
  ],
  "exclude": {
    "min": [118, 50, -22],
    "max": [122, 90, -18]
  },
  "tags": [
    "stardewcraft:outdoor",
    "myaddon:orchard"
  ],
  "priority": 50
}
```

`include` 接受单个 box 或 box 数组并取并集，`exclude` 从并集中挖除任意数量的
box；点可写成 `min=max`，二维区域可给出完整的 Y 范围。若某个逻辑地点没有绑定
区域，它继续使用原 `locations` 的 `min/max`，所以旧数据完全不变；一旦为该地点
提供区域，精确区域就取代粗边界参与 `StardewLocations.find`。这样不规则或分离
的地图布局不会因为外包围盒互相误判。区域 reload 同样整批原子替换。

Java 附属可用 `StardewRegions.get/find/findAll/all/withTag/forLocation` 查询同一
目录。`priority` 高者先返回，平级按完整 ID；标签只用于分类和筛选，不自行触发
玩法。钓鱼地点与遗物点通过逻辑地点间接获得精确区域能力，后续世界系统应复用
这里，而不是新增私有坐标表。

采集区另有一个向后兼容的精确约束：若
`forage_zones/myaddon:path.json` 与 `regions/myaddon:path.json` 拥有相同 ID，
旧 `areas` 继续作为带权随机候选包围盒，但生成和已有采集物计数都必须落在该精确
region 内。没有同 ID region 的所有旧采集区行为不变。这样既不修改已经稳定的
采集区 schema，也允许地图附属为弯曲、分离或带洞的生成区域提供统一几何。

需要响应玩家进入、离开或跨维度时，不要在附属中再开一套坐标轮询：

```java
StardewLocationEvents.register(
    ResourceLocation.fromNamespaceAndPath("myaddon", "orchard_events"),
    100,
    transition -> {
        if (transition.enteredLocation()
                && orchardId.equals(transition.currentLocation())) {
            // 启动附属自己的服务端逻辑。
        }
    }
);
```

事件在服务端玩家 tick 的最终逻辑地点改变后发送，包含玩家、前后地点、前后维度、
方块位置与 `INITIAL / LOCATION_CHANGED / DIMENSION_CHANGED / LOGOUT` 原因。地图
reload 导致站立玩家的最终地点发生变化，也会在下一 tick 走同一事件。监听器按
优先级和完整 ID 排序；异常只隔离当前监听器，不能取消移动，也不会阻止后续附属。

可以被多个系统引用的单点坐标使用世界锚点：

```text
data/myaddon/anchors/orchard_stage.json
```

```json
{
  "dimension": "stardewcraft:stardew_valley",
  "position": [120.5, 64, -32.5],
  "yaw": 180,
  "indoor": false,
  "use_ground_height": false,
  "location": "myaddon:orchard",
  "roles": [
    "stardewcraft:npc_schedule",
    "stardewcraft:festival_stage"
  ]
}
```

文件 ID 即锚点 ID `myaddon:orchard_stage`。`position` 是精确实体坐标，不会自动
加 `0.5`；需要方块中心时应直接写半格坐标。`roles` 是供目录筛选和诊断使用的
命名空间标签，不会单独触发玩法。NPC 日程可写 `@myaddon:orchard_stage`，服务端
会验证锚点维度并使用其位置、室内标记和地面高度策略；本体旧
`npc_route_points.json` 仍照常读取，并自动投影到统一目录。本体文件中的
`town_square` 变为 `stardewcraft:town_square`，附属自己的同名文件则归入该
附属命名空间；新的 `anchors/*.json` 对同 ID 拥有明确优先级。这一适配不改写旧
文件，也不改变旧坐标的方块居中和地面高度语义。

Java 附属和只读集成可以使用 `StardewWorldAnchors.get/resolve/all/withRole`。
锚点 reload 采用整批原子替换：任一文件无效时保留上一份活动目录，不发布半套
坐标。Portal Trigger 的目标 ID 现在可以直接写锚点 ID；若没有同 ID 的显式
`interior_portals` 目标，本体会使用锚点坐标和 yaw，并在实际传送前验证当前维度。
这只解析目的地，不会自动在世界中生成 Portal Trigger，也不会替附属定义进入条件。
锚点本身不会自动放置节日结构；只有显式注册并由节日定义引用的 overlay 才会
执行地图替换。

### 通用地图槽位

世界锚点和农场布局挂点会同时投影为解析后的 `StardewMapSlot`。消费系统不再需要
分别理解“绝对 anchor”和“农场相对 attachment”；统一视图始终包含最终维度、
世界坐标、yaw、室内/地面高度策略、角色和来源作用域：

```java
Optional<StardewMapSlot> stage = StardewMapSlots.playerFarm(
    server,
    playerUuid,
    ResourceLocation.fromNamespaceAndPath("myaddon", "festival_stage")
);

List<StardewMapSlot> buildingSlots =
    StardewMapSlots.playerFarmWithRole(
        server,
        playerUuid,
        StardewMapSlotRoles.BUILDING
    );
```

槽位 ID 只要求在自己的作用域内唯一。完整身份是
`scopeType + scopeId + slotId`：世界锚点使用
`stardewcraft:world / global`，农场实例使用
`stardewcraft:farm / <owner UUID>`，`containerId` 分别指向可选地点或农场布局。
需要保存引用时必须保存这个复合身份，不能假设两个玩家农场里的同名挂点是同一个
世界点。`StardewMapSlots.get(...)` 可重新解析复合身份；移除布局附属后会返回空，
不会错误回退到另一个农场。

`StardewMapSlotRoles` 提供 NPC、NPC 日程、节日、节日舞台、建筑和 Portal 的公共
能力 ID；附属仍可组合自己的命名空间 role。旧
`StardewWorldAnchors`、`StardewFarmLayoutAttachment` 与
`StardewFarmLayoutAttachmentKeys` 全部保留，后者的通用 role 常量现在只是共享
槽位 role 的兼容别名。槽位目录是服务端只读能力，不会把其他玩家的农场坐标同步
给客户端，也不会自行放置结构或绕过建筑/传送权限。

## 建筑蓝图与目录会话

建筑商品使用：

```text
data/<namespace>/building_blueprints/<path>.json
```

文件路径是稳定蓝图 ID。`builder` 是命名空间目录 ID，不要求对应本体 NPC：

```json
{
  "builder": "myaddon:orchard_carpenter",
  "order": 10,
  "display_name": "building.myaddon.storehouse",
  "description": "building.myaddon.storehouse.desc",
  "money": 2500,
  "materials": [
    {"item": "minecraft:oak_log", "count": 64},
    {"item": "minecraft:stone", "count": 32}
  ],
  "result_item": "myaddon:storehouse",
  "available_when": [
    {
      "type": "stardewcraft:location",
      "data": {"location": "myaddon:orchard"}
    }
  ],
  "tags": ["stardewcraft:storage"],
  "properties": {"myaddon:placement_family": "orchard"}
}
```

完整约束见 `docs/schemas/building-blueprint-v1.schema.json`。任一文件字段拼错、
物品引用失效、材料重复或 Condition 无法解码时，整批 reload 回滚。数据蓝图与
Java 蓝图同 ID 也会拒绝，不以加载顺序静默覆盖。

Java 附属使用 `StardewBuildingBlueprints.register` 注册同一
`StardewBuildingBlueprintDefinition`，使用 `find/all/forBuilder` 查询。
附属在自己的 NPC、方块、任务或地点权限检查通过后调用：

```java
StardewBuildingBlueprints.open(player, MY_CARPENTER);
```

`open` 只发送当前玩家可见的条目，并签发一分钟的服务端目录会话。购买请求同时
携带 builder、稳定蓝图 ID 和目录 revision；服务端重新验证会话、Condition、
金额、材料、结果物品和 Wizard 距离，不再信任列表下标。材料会先形成完整槽位
消费计划，付款成功后才一次性扣除；产物背包放不下时安全掉落。旧
`RobinService/WizardBuildingService.getBlueprints` 与旧 payload 构造器暂时保留
源兼容，但没有服务端会话的旧式购买请求不会获准。

该目录当前负责“购买一个可放置的注册物品”，不会把任意 JSON 变成新方块或直接
修改世界结构。附属物品可以实现自己的放置逻辑；升级路径与自由形状施工状态会在
建筑生命周期层扩展，而不是在购买包中加入附属私有分支。

统一扩展注册表可由管理员查看：

```text
/stardew debug extensions list
/stardew debug extensions explain stardewcraft:farm/layout
/stardew debug extensions state-keys
/stardew debug world here
/stardew debug world locations [namespace:id]
/stardew debug world anchors [namespace:id]
/stardew debug world slots
/stardew debug world regions [namespace:id]
/stardew debug festival [namespace:id]
/stardew debug building-blueprints
/stardew state export farm <owner-uuid>
/stardew state export animal <animal-id>
/stardew state export festival <namespace:id>
/stardew state export community-center <player-uuid>
/stardew state repair <farm|animal|festival|community-center> ... <entry> preview
/stardew state repair <farm|animal|festival|community-center> ... <entry> confirm <token>
```

输出包含扩展点 revision、最终调用顺序、注册 ID 与优先级；`state-keys` 还会列出
scope、Key ID 和当前 schema 版本。`world here` 解释管理员当前位置最终命中的
逻辑地点、全部区域、当前音乐决策、该处商店绑定的 Condition 是否通过，以及
脚下通用机器的周期类型、自动化来源、输入、产物和剩余时间；
其余 world 子命令列出或解释粗边界、精确几何、锚点来源、
槽位复合作用域、角色和优先级。`festival` 汇总 mechanic ID、旧 Handler 兼容层、可组合贡献、
能力和缺失引用。命令只读且要求权限等级 2。Java 诊断工具可使用
`StardewExtensions.snapshot()` 与 `StardewStateDiagnostics.registeredKeys()`
读取同一份不可变信息。

`stardew state export` 要求权限等级 3，将指定对象的 scope、对象身份、诊断集合和原始
entries 作为压缩 NBT 写入当前世界的 `stardewcraft-state-exports` 目录。文件名只使用经过
清洗的对象身份和导出时间；导出读取防御性副本，不修改状态也不标脏存档。它用于在执行任何
orphan 修复前保留可恢复原件。

`stardew state repair` 同样要求权限等级 3，并且必须分两步执行。`preview` 只接受 orphan、
损坏 envelope 或非法原始名称，健康条目和仅版本落后的合法条目不会生成删除计划；输出包含
问题分类和基于当前原始 entry 生成的短确认 token。`confirm` 必须提供同一个 token，并会先
自动写出完整备份；备份失败、entry 变化、问题已消失或 token 不匹配时都不会删除。确认成功
后只删除这一条 raw entry，不清理同一命名空间的其它状态。

已经持久化的命名空间状态可在对应领域对象上读取
`StardewStateContainerSnapshot`：

```java
StardewStateContainerSnapshot state =
    farmPersistentData.diagnostics();
```

农场、动物和节日会话同时提供按服务端对象 ID 查询的静态 `diagnostics(...)`；
社区中心提供按玩家 UUID 查询的静态入口。快照稳定列出该 scope 的已存储与已注册
ID，并分别标记 orphan、NBT envelope 损坏、低于当前 schema 的旧版本、高于当前
schema 的未来版本和无法解析成资源 ID 的原始名称。同一条目可以同时属于多个问题
集合，例如缺席附属留下的损坏条目同时是 orphan 与 malformed。该 API 只读，不暴露
原始 NBT，也不会迁移、删除或重写任何数据；诊断前后未知条目仍原样保存。

持有原始不可伪造 `Key` 的附属可以为自己的旧版本条目生成迁移预览，再显式提交：

```java
Optional<StardewStateMigrationPreview> preview =
    StardewFarmPersistentData.previewMigration(
        server,
        ownerUuid,
        FARM_STATE,
        (storedVersion, targetVersion, payload) -> {
            payload.putBoolean("new_field", true);
            return payload;
        });

preview.ifPresent(candidate -> {
    StardewStateMigrationResult result =
        StardewFarmPersistentData.applyMigration(
            server, ownerUuid, FARM_STATE, candidate);
});
```

预览只操作防御性副本，不标脏存档；只有旧于 Key 当前版本的合法 envelope 才会产生预览。
`applyMigration` 会再次核对 scope、Key、源版本和完整源 payload。预览之后数据若被其它逻辑
修改，会返回 `STALE` 且不覆盖新数据；对象或条目消失时返回 `MISSING`。动物、节日会话和
社区中心玩家状态提供相同的 `previewMigration/applyMigration` 流程。该能力只允许迁移
调用者自己持有 Key 的条目，不能读取或修改 orphan。

orphan 原始导出以及需要管理员显式确认的删除/修复属于管理层，不能用诊断或迁移调用替代。

## 节日定义

每个文件定义一个节日，文件路径就是命名空间 ID：

```text
data/<namespace>/festivals/<path>.json
```

```json
{
  "type": "passive",
  "display_name": "Apple Day",
  "season": 2,
  "start_day": 5,
  "end_day": 5,
  "start_time": 900,
  "end_time": 1400,
  "start_message_key": "myaddon.festival.apple_day.started",
  "available_when": [],
  "world": {
    "location": "Town",
    "map_overlay": "",
    "map_replacements": {},
    "shops": [],
    "mechanic_id": ""
  }
}
```

`season` 为春夏秋冬对应的 `0..3`。`type=passive` 允许玩家在开放时段照常行动；`active` 用于会接管玩家并进入主事件流程的节日。定义使用原子 reload，任一无效文件会拒绝整次候选快照；服务端快照会在登录和 `/reload` 后同步给客户端日历。

`available_when` 是世界级条件，主动与被动节日使用相同的服务端判定。它不得使用玩家背包、金钱、个人旗标或个人技能等需要玩家上下文的内置 Condition；这类定义会在 reload 时被拒绝。

`legacy_id`、`legacy_condition` 和 `presentation` 只用于本体原版数据兼容。
新内容应使用文件 ID 和公共 `available_when`。没有特殊玩法的节日可以把
`mechanic_id` 留空；复杂节日由多个独立 mechanic layer 组合：

```java
StardewFestivalMechanics.register(
    MY_REWARD_LAYER,
    100,
    ResourceLocation.fromNamespaceAndPath("myaddon", "apple_day"),
    Set.of(
        StardewFestivalMechanicCapability.REWARDS,
        StardewFestivalMechanicCapability.PERSISTENT_STATE),
    new StardewFestivalMechanicHandler() {
        @Override
        public void onSessionChanged(
            StardewFestivalMechanicContext context,
            StardewFestivalSessionEvent event
        ) {
            // 只接收 mechanic_id=myaddon:apple_day 的会话。
        }
    }
);
```

然后在 JSON 的 `world.mechanic_id` 写 `apple_day` 或
`myaddon:apple_day`；附属数据中的裸 ID 自动归入文件命名空间。本体旧节日和已有
附属可继续使用 `ActiveFestivalHandlers.register` /
`PassiveFestivalHandlers.register`，它们作为兼容层保留。新 contribution 按优先级
稳定排序、逐项异常隔离，同一个 mechanic 可以分别由 NPC、小游戏、奖励、货币和
客户端展示附属叠加，不需要争夺一个总 Handler。能力是发现信息，不会绕过服务端
校验；可用 `StardewFestivalMechanics.inspect(festivalId)` 查看最终组合。
地图覆盖 ID 必须已经存在于地图覆盖注册表，数据定义不会凭空创建 schematic 或
地图补丁。

需要节日临时替换地图时，优先使用纯数据定义：

```text
data/myaddon/festival_map_overlays/apple_day.json
```

```json
{
  "location": "orchard",
  "origin_anchor": "orchard_overlay_origin",
  "festival_schematic": "festivals/apple_day.schem",
  "bounds_min_offset": [-4, 0, -6],
  "bounds_max_offset": [40, 12, 34],
  "safe_position_offsets": [
    [2, 0, 2]
  ],
  "requires_black_fade": true,
  "cleanup_dropped_items": true,
  "cleanup_tagged_entities": true,
  "tree_clearance": {
    "horizontal_radius": 0,
    "up": 0,
    "down": 0
  }
}
```

不带命名空间的 `location`、`origin_anchor`、`base_schematic` 和
`festival_schematic` 自动归入文件所在命名空间。省略 `base_schematic` 表示应用
前保存现场方块并在结束时恢复；若指定它，则使用固定 base/festival 差分。三个
清理布尔值默认 `true`，安全点和树木清场可省略。场地定义整批原子 reload：任一
JSON 无效或与 Java 注册同 ID 时，上一批数据场地继续生效，不发布半套结果。
场地开始应用时会把实际 patch 持久化进世界会话；即使随后移除或修改数据包，
进行中的场地仍能按原 patch 完成并恢复，不会拿新坐标或新结构覆盖旧会话。

需要运行时组装描述的 Java 附属也可以注册同一个实验性模型：

```java
StardewFestivalMapOverlays.register(new StardewFestivalMapOverlay(
    ResourceLocation.fromNamespaceAndPath("myaddon", "apple_day"),
    ResourceLocation.fromNamespaceAndPath("myaddon", "orchard"),
    ResourceLocation.fromNamespaceAndPath("myaddon", "orchard_overlay_origin"),
    null,
    ResourceLocation.fromNamespaceAndPath(
        "myaddon", "festivals/apple_day.schem"),
    new BlockPos(-4, 0, -6),
    new BlockPos(40, 12, 34),
    List.of(new BlockPos(2, 0, 2)),
    true, true, true,
    StardewFestivalMapOverlay.TreeClearance.NONE
));
```

`originAnchor` / 第三个参数引用
`data/myaddon/anchors/orchard_overlay_origin.json`。边界和安全点均相对该锚点；
结构 ID 对应
`data/myaddon/structures/festivals/apple_day.schem`。`baseSchematic=null` 表示
应用前保存现场方块并在节日结束时恢复，适合与其它地图附属组合；指定 base
structure 时沿用固定 base/festival 差分。实际应用会校验锚点维度，缓存键包含
解析后的原点和结构资源，reload 后不会误用旧坐标的 patch。

节日 JSON 的 `world.map_overlay` 写完整 ID `myaddon:apple_day` 即可引用。这个
接口开放的是场地替换和恢复，不会自动生成节日会话、NPC、小游戏或奖励；这些由
节日定义、统一会话 facade 与 mechanic Handler 分别提供。

节日机制读取会话时不需要持有内部可变对象：

```java
Optional<StardewFestivalSessionSnapshot> session =
    StardewFestivalSessions.find(
        level,
        ResourceLocation.fromNamespaceAndPath("myaddon", "apple_day"));
```

快照包含规范 festival ID、兼容 runtime ID、日期、会话阶段、地图恢复阶段和参与者
集合，所有集合均不可变。`all(level)` 可用于管理员诊断和只读集成。

所有主动和被动节日的会话状态变化共享同一个观察入口：

```java
StardewFestivalSessionEvents.register(MY_SESSION_OBSERVER, 100, event -> {
    switch (event.type()) {
        case PHASE_CHANGED -> onPhaseChanged(
            event.session(), event.previousPhase().orElseThrow());
        case MAP_PHASE_CHANGED -> onMapChanged(
            event.session(), event.previousMapPhase().orElseThrow());
        case PARTICIPANT_JOINED -> onJoined(
            event.session(), event.participant().orElseThrow());
        case PARTICIPANT_LEFT -> onLeft(
            event.session(), event.participant().orElseThrow());
    }
});
```

事件在状态修改完成后发出，携带真实 `ServerLevel` 和新的不可变会话快照。同一阶段
重复赋值、同一玩家重复加入/离开不会重复发事件；读档只恢复状态，也不会伪造历史事件。
Listener 异常按注册项隔离，不能阻止节日阶段、地图恢复或参与者保存。

附属不应直接修改内部 `FestivalSessionState`。统一参与者入口会重新解析当前定义和
服务端阶段，并返回机器可读结果：

```java
StardewFestivalParticipantResult joined =
    StardewFestivalParticipants.join(player, festivalId);
StardewFestivalParticipantResult left =
    StardewFestivalParticipants.leave(level, festivalId, player.getUUID());
```

主动节日沿用完整入口开放检查；被动节日要求当前会话处于 `OPEN` 或
`MAIN_EVENT`。成功操作自动持久化、发出统一事件并同步客户端。

客户端只读集成使用 `StardewFestivalClientSessions`。服务端在登录及每次会话变化
后发送完整替换快照，最多 64 条，优先保留未关闭及最新会话。DTO 只包含阶段、
地图阶段、参与者总数和“本地玩家是否参与”，不会传输其他玩家 UUID 或附属 NBT。
这份有界 DTO 适合 HUD、日历和附属 UI；需要参与者身份或持久状态的逻辑必须留在
服务端。网络快照同时携带每个实际服务器实例独有的同步纪元；客户端只在同一纪元
内按 revision 丢弃乱序旧包，因此服务器重启后从较小 revision 重新开始不会保留
上一次连接的陈旧会话。

节日 JSON 的 `world.shops` 不再只是展示元数据。附属 NPC、交互方块或小游戏在
服务端可以读取规范 ID，并走同一套商店过滤、库存、复合货币和购买协议：

```java
List<StardewFestivalShopSnapshot> shops =
    StardewFestivalShops.list(festivalId);
StardewFestivalShopOpenResult opened =
    StardewFestivalShops.open(player, festivalId, shops.getFirst().shopId());
```

目录同时保留规范 `shopId` 和旧购买协议需要的 `runtimeShopId`。打开操作会重新验证
节日存在、会话为 `OPEN/MAIN_EVENT`、商店确实列在该节日中、玩家位于声明地点；
主动节日还要求玩家已经参与，被动节日则在合法地点自动加入。附属无需自行构造
`OpenShopScreenPayload`，也不能用任意 shop ID 绕过节日定义。

一次性奖励使用两阶段 Provider，不需要每个小游戏各自发明领取标记：

```java
StardewFestivalRewards.register(MY_REWARD_HANDLER, 100, context ->
    context.rewardId().equals(MY_REWARD)
        ? StardewFestivalRewardPreparation.accept(grantContext ->
            giveReward(grantContext.player()))
        : StardewFestivalRewardPreparation.pass()
);

StardewFestivalRewardClaimResult result =
    StardewFestivalRewards.claim(player, festivalId, MY_REWARD);
```

Handler 拥有的动态奖励不会被核心扫描或猜测。需要让菜单、图鉴和诊断发现它时，
显式注册一条只读描述：

```java
StardewFestivalRewards.registerDescriptor(
    MY_REWARD_DESCRIPTOR,
    100,
    new StardewFestivalRewardDescriptor(
        festivalId,
        MY_REWARD,
        List.of(StardewRewardComponent.item(
            ResourceLocation.parse("myaddon:golden_apple"), 1)),
        true
    )
);

List<StardewFestivalRewardDescriptor> rewards =
    StardewFestivalRewards.catalog(festivalId);
StardewProgressSnapshot state = StardewProgress.inspect(
    player, StardewFestivalRewards.progressKey(festivalId, MY_REWARD));
StardewRewardPreview preview = StardewRewardPreviews.preview(
    player, StardewFestivalRewards.progressKey(festivalId, MY_REWARD));
StardewRequirementReport preflight =
    StardewFestivalRewards.requirements(player, festivalId, MY_REWARD);
```

描述符是展示目录，不是授权结果。`previewExhaustive` 仅表示成功领取时预览是否完整；
它不表示当前玩家一定能够领取。公开进度中的 `AVAILABLE` 只表示会话开放、玩家参与
且尚未领取，不会伪造 `rewardClaimable=true`；调用方仍必须执行 `claim`，由权威
Handler 判断小游戏成绩、背包容量和其它动态约束。派生 domain 保留 festival
命名空间和完整 path，reward ID 仍保持自己的命名空间，因此多个附属不会因字符串
拼接发生碰撞。

领取前会重新验证会话为 `OPEN/MAIN_EVENT` 且玩家已经参与。Provider 按优先级依次
返回 `PASS/ACCEPT/REJECT`，prepare 与 grant 异常均隔离；只有 grant 返回成功后
才写入会话级 `(rewardId, player UUID)` 领取记录。重复调用返回
`ALREADY_CLAIMED`，记录随会话 NBT 保存。Provider 应先完成容量等预检，再让 grant
执行一个原子领域操作；物品、货币、旗标或任务奖励继续调用各自 API，不在这里
复制一套万能奖励格式。显式描述过的奖励领取成功后会从 `AVAILABLE` 进入
`COMPLETED`，并发布带真实玩家 actor 和 `FESTIVAL_REWARD` cause 的统一
`REWARD_CLAIMED` 事件。

小游戏和其它可交互活动使用稳定 activity ID，而不是让外部代码调用某个本体
FestivalService 的私有方法：

```java
StardewFestivalActivities.register(
    MY_ACTIVITY_HANDLER,
    100,
    MY_MECHANIC,
    MY_APPLE_TOSS_ACTIVITY,
    context -> {
        openAddonMinigame(context.player());
        return StardewFestivalActivityDecision.STARTED;
    }
);

StardewFestivalActivityResult started =
    StardewFestivalActivities.start(
        player, festivalId, MY_APPLE_TOSS_ACTIVITY);
```

注册项按优先级稳定排序并可通过 `registrations(mechanicId)` 发现。`start` 只能从
受信任的服务端 NPC/方块/菜单处理器调用；它会验证 festival 与 mechanic 的绑定、
会话阶段、参与者和可解析的声明逻辑地点，再异常隔离地调用匹配 Handler。旧本体
仍在使用且尚未进入逻辑地点目录的 location 字符串保留兼容放行；附属命名空间地点
必须能解析并匹配。公共 API 不提供
一个“客户端任意 activity ID”请求包；需要客户端按钮时，附属自己的小型 C2S
payload 仍应先验证交互距离和菜单上下文，再调用这里。

需要让菜单、HUD 和诊断看到小游戏分数时，使用 festival 派生 domain 注册普通
`StardewProgressProvider`：

```java
ResourceLocation domain =
    StardewFestivalActivities.progressDomain(festivalId);
StardewProgressKey key =
    StardewFestivalActivities.progressKey(festivalId, activityId);

StardewProgress.registerProvider(
    MY_ACTIVITY_PROGRESS,
    100,
    domain,
    new StardewProgressProvider() {
        public StardewProgressSnapshot inspect(
                ServerPlayer player, ResourceLocation entryId) {
            return entryId.equals(activityId)
                ? myAuthoritativeActivitySnapshot(player, key)
                : null;
        }

        public Collection<ResourceLocation> entries(
                ServerPlayer player) {
            return List.of(activityId);
        }
    });
```

派生 domain 保留 festival 的命名空间和完整 path，例如
`myaddon:apple_day + other:apple_toss` 会得到
`domain=myaddon:festival_activity/apple_day`、`id=other:apple_toss`。因此不会
把两个 namespaced ID 拼成需要转义的模糊字符串，也允许同名 activity 在不同节日
拥有独立状态。本体寻蛋作为首个适配 canary，公开鸡蛋数目标并在实际捡蛋提交后发布
统一 `PROGRESSED`；其它小游戏只有在其权威实现或附属显式提供 Provider 后才进入
目录。

附属机制的跨 tick/重启状态使用统一命名空间存储：

```java
StardewFestivalSessionPersistentData.Key SESSION_STATE =
    StardewFestivalSessionPersistentData.register(
        ResourceLocation.fromNamespaceAndPath(
            "myaddon", "apple_day_state"),
        2
    );

CompoundTag state = new CompoundTag();
state.putInt("apples_delivered", 12);
StardewFestivalSessionPersistentData.write(
    level, festivalId, SESSION_STATE, state);
```

写入需要注册返回的 Key，并自动标记 `FestivalWorldData`。会话 NBT 使用与动物、
农场和社区中心相同的 `{version, payload}` 信封；附属缺席时未知条目会原样跨读写
保留。当前状态随对应节日会话生命周期保存；若需要跨多届节日永久累计，应使用
未来的世界/玩家 scope，而不是把历史会话当作全局数据库。

## NPC 命名空间与交互 Provider

`data/<namespace>/npc/dialogue|schedules|tastes/*.json` 中，不带命名空间的 `npc_id` 和文件名会自动归入文件所在的数据包命名空间。本体 `stardewcraft` 文件继续保留 `lewis` 等旧运行 ID，公共 API 会把它们投影为 `stardewcraft:lewis`；附属的 `apple_keeper.json` 则对应 `myaddon:apple_keeper`。`npc/capabilities/*.json` 数组中的 `id` 使用同一规则。

新 NPC 的静态身份优先通过统一 Profile 目录注册一次：

```java
StardewNpcProfiles.register(MY_PROFILE_REGISTRATION, 100,
    new StardewNpcDefinition(
        MY_NPC_ID,
        new StardewNpcProfile(
            MY_NPC_ID, true, true, "idle_walk",
            0, 0, 0, 0, 1, false),
        new StardewNpcDisplay(
            MY_NPC_ID,
            "entity.myaddon.npc.archivist",
            id("textures/portraits/archivist.png"), 128, 320,
            id("textures/mugshots/archivist.png"), 16, 24,
            "myaddon.relationship.archivist", false)));
```

同一个定义同时成为服务端社交能力和客户端展示的权威静态身份。注册条目会进入
`StardewNpcProfiles.ids()`，因此即使它不在本体 capability 表中，也能被社交概览
枚举；年龄、礼貌和可约会能力也会进入友情上限、礼物反应与垃圾桶反应。本体数据
NPC 会自动投影到同一目录。多个附属定义同一 NPC 时按优先级和注册 ID 稳定选择。
既有 `StardewNpcDisplays` Provider 仍保留，并可作为更细粒度的展示覆盖层，旧附属
无需立即迁移。

Profile 不会假装实现它没有实现的运行时系统。实体查找、条件社交、送礼、交互、
友情奖励、数据日程和数据对话仍由下面的独立组合入口提供；统一目录负责让这些
入口共享同一个命名空间身份，而不是把动态逻辑塞进客户端 DTO。

`StardewNpcContents.inspect(npcId)` 会把当前原子 reload 快照中的 Profile、对话、
日程、喜好和 NPC 商店绑定聚合成只读 `StardewNpcContentSnapshot`。它会报告绑定
引用不存在的商店，以及只有孤立内容却没有 Profile 的 NPC。服务端可以传入
`ServerLevel` 获得不泄漏实体实例的 `StardewNpcRuntimeSnapshot`，确认当前实体
resolver 是否能找到存活实体。运维命令提供同样的证据：

```text
/stardew debug npc
/stardew debug npc myaddon:archivist
```

列表与诊断都使用当前快照，不缓存附属缺席时的推测结果。

附属可以在本体任务交付、商店、送礼和普通对话之前注册交互 Provider：

```java
StardewNpcInteractions.register(MY_PROVIDER_ID, 100, context -> {
    if (!context.npcId().equals(ResourceLocation.fromNamespaceAndPath("stardewcraft", "lewis"))) {
        return InteractionResult.PASS;
    }
    return openMyScreen(context.player()) ? InteractionResult.SUCCESS : InteractionResult.PASS;
});
```

Provider 按优先级从高到低、同优先级按完整 ID 排序。返回 `PASS` 会继续下一个 Provider 和本体流程；返回其它结果表示已经处理。重复 Provider ID 会立即抛错；运行时异常会记录具体 Provider 和 NPC ID，然后继续本体流程。

### 社交规则与友情快照

`StardewNpcSocialRules` 覆盖五个彼此独立的决策：能否社交、能否收礼、是否显示在社交页、是否为社交页建立初始友情，以及是否计入“认识所有人”。Provider 得到客户端无关的 `StardewNpcProfile` 和只读 `StardewNpcFriendshipSnapshot`，不需要访问 `NpcCapabilityProfile` 或可变存档对象：

```java
StardewNpcSocialRules.register(MY_SOCIAL_PROVIDER, 100,
    (context, rule, proposed) -> {
        if (!context.npcId().equals(MY_NPC_ID)) {
            return StardewNpcSocialRules.Decision.PASS;
        }
        return switch (rule) {
            case CAN_SOCIALIZE, CAN_RECEIVE_GIFTS,
                 SHOW_ON_SOCIAL_PAGE,
                 CREATE_FRIENDSHIP_FOR_SOCIAL_PAGE ->
                    StardewNpcSocialRules.Decision.ALLOW;
            case INCLUDE_IN_INTRODUCTIONS ->
                    StardewNpcSocialRules.Decision.PASS;
        };
    });
```

按优先级遇到第一个 `ALLOW` 或 `DENY` 后停止；全部 `PASS` 时使用本体结果。玩家无关的查询中 `context.player()` 为 `null`。Provider 异常会记录注册 ID 并继续后续 Provider。

### NPC 实体解析

活动 NPC、附属 NPC或 Joja 线 NPC 不一定属于本体常驻追踪表。`StardewNpcEntities` 允许按标准 NPC ID 查找当前服务端世界中的实体：

```java
StardewNpcEntities.register(MY_ENTITY_RESOLVER, 100, context -> {
    if (!context.npcId().equals(MY_NPC_ID)) return null;
    for (Entity entity : context.level().getAllEntities()) {
        if (entity.getTags().contains("myaddon_my_npc")) return entity;
    }
    return null;
});
```

返回值必须仍在同一个 `ServerLevel`、存活且未移除；无效候选会被忽略。本体常驻追踪仍作为最后的默认 resolver。确认送礼先保留旧 `NpcSpawnManager.getTrackedNpc` 调用，再在结果为空时使用公共 resolver，因此已有 redirect 目标仍然稳定，而迁移后的附属不再需要注入该方法。

核心调度实体的真实生成和移除会发出不可否决的生命周期事实：

```java
StardewNpcLifecycleEvents.register(MY_LIFECYCLE_OBSERVER, 100, event -> {
    if (event.phase() == StardewNpcLifecyclePhase.SPAWNED) {
        indexNpc(event.npcId(), event.level().dimension().location(),
            event.entityUuid());
    } else {
        removeNpcIndex(event.npcId(), event.entityUuid());
    }
});
```

事件包含 NPC ID、服务端世界、实体 UUID 和稳定的原因字符串；Listener 按优先级
和注册 ID 排序，异常只隔离当前 Listener。附属自己拥有实体创建与移除流程时，
分别调用 `announceSpawned` / `announceRemoved` 上报同一种事件。上报不会注册、
生成或删除实体，也不能把客户端实体伪装成服务端生命周期。

### 礼物确认与前后钩子

附属只想给已有 NPC 增删自己的物品喜好时，不应覆盖完整
`npc/tastes/<npc>.json`。使用领域化 patch：

```text
data/<namespace>/npc/taste_patches/<path>.json
```

```json
{
  "npc": "stardewcraft:abigail",
  "priority": 100,
  "add": {
    "loved": ["myaddon:orchard_apple"]
  },
  "remove": {
    "disliked": ["minecraft:apple"]
  }
}
```

允许的分类是 `loved`、`liked`、`neutral`、`disliked` 和 `hated`。patch 从低
优先级到高优先级应用，同优先级按完整文件 ID 排序；单个 patch 先删除、后追加，
并保持集合顺序稳定。默认 `"required": true`，目标 NPC 喜好表不存在时会拒绝
本次 NPC reload；可选兼容 patch 可写 `false` 并在目标不存在时跳过。

未知物品、未知分类、同一分类同时增删同一物品、重复项或空 patch 都会拒绝整批
patch，并保留上一份完整 NPC 快照。有效 patch 自身以及最终 NPC 喜好中的精确物品
都会进入统一内容图。这样多个物品附属可以组合修改同一 NPC，而不复制其对话、
日程、消息文案或其它附属已经增加的喜好。

Minecraft 数据包优先级仍可覆盖同一资源路径；loader 最终只会看到胜出的文件。
如果两个不同资源路径却声明了同一个 dialogue、schedule、taste、event 或 capability
逻辑 ID，则属于无法解释来源的冲突，会列出两个资源 ID、拒绝整个 NPC 候选并保留
旧快照，不再依赖遍历顺序静默选择最后一个。

礼物扩展分成三个独立注册表：

```java
StardewNpcGifts.registerConfirmationPolicy(MY_CONFIRMATION, 100, context ->
    context.npcId().equals(MY_NPC_ID) && context.player().isShiftKeyDown()
        ? StardewNpcGifts.Confirmation.GIVE_IMMEDIATELY
        : StardewNpcGifts.Confirmation.PASS);

StardewNpcGifts.registerBeforeHook(MY_GUARD, 100, context ->
    mayGive(context.player(), context.npcId(), context.gift())
        ? StardewNpcGifts.BeforeDecision.PASS
        : StardewNpcGifts.BeforeDecision.DENY);

StardewNpcGifts.registerAfterHook(MY_OBSERVER, 100, result -> {
    if (result.status() == StardewNpcGifts.Status.ACCEPTED) {
        recordGift(result.npcId(), result.taste(), result.friendshipDelta());
    }
});
```

确认策略只在本体已判定“当前物品可以送给该 NPC”后运行，不能把无效物品伪装成礼物。`REQUIRE_CONFIRMATION` 保留现有弹窗，`GIVE_IMMEDIATELY` 仍调用同一个服务端确认入口，`SKIP_GIFT` 则把本次交互交还普通对话。正式确认时仍会重新读取手持物，任务交付优先于礼物钩子；`BeforeHook.DENY` 发生在普通礼物的任务 25、友情、物品扣除和音效之前。`AfterHook` 会收到防御性物品副本、接受/日限/周限状态、口味来源、生日倍率结果、友情变化和最终点数。冬日星盛宴的秘密礼物也走 before/after hook，但没有确认策略。

### 友情奖励

友情奖励 Handler 在本体奖励之后按稳定顺序执行：

```java
StardewNpcFriendshipRewards.register(MY_TWO_HEART_REWARD, 100, context -> {
    if (!context.npcId().equals(MY_NPC_ID) || context.points() < 500) {
        return StardewNpcFriendshipRewards.Outcome.PASS;
    }
    giveReward(context.player());
    return StardewNpcFriendshipRewards.Outcome.COMPLETE;
});
```

`CHANGED` 表示本次有变化但将来还要继续检查，适合一个 Handler 管理多个阈值；`COMPLETE` 由本体按“玩家 + 注册 ID”持久化一次性完成标记；`COMPLETE_WITHOUT_REWARD` 只记录完成；`PASS` 不改状态。异常只影响当前 Handler。登录补发路径调用同一个 `applyEligibleRewards`，所以错过在线触发的奖励仍可补发。

### 客户端展示 DTO 与旧 Provider

`StardewNpcDisplays` 在客户端和服务端都可安全加载，不包含 Screen 或渲染器类型。它提供名称翻译键、对话头像、社交页 mugshot、纹理尺寸、关系翻译键与可约会标志：

```java
StardewNpcDisplays.register(MY_DISPLAY_PROVIDER, 100, npcId ->
    npcId.equals(MY_NPC_ID)
        ? new StardewNpcDisplay(
            MY_NPC_ID,
            "entity.myaddon.npc.archivist",
            id("textures/portraits/archivist.png"), 128, 320,
            id("textures/mugshots/archivist.png"), 16, 24,
            "myaddon.relationship.archivist", false)
        : null);
```

社交页名称、排序、mugshot、可约会心数，以及通用 NPC 对话头像都会读取该 DTO。客户端缺少 mugshot 时该 NPC 不进入现有社交表，避免绘制损坏纹理；未注册 Provider 时按 NPC 命名空间生成兼容默认资源路径。附属必须在客户端和服务端都安装并以相同顺序注册这些公共入口。

## 钓鱼与收集系统

现代定义路径：

```text
data/<namespace>/fishing/treasure_pools/<path>.json
data/<namespace>/fishpond/pond_data/<path>.json
data/<namespace>/adventurers_guild/monster_slayer_goals/<path>.json
data/<namespace>/museum_rewards/rewards/<path>.json
data/<namespace>/museum/lost_books/<path>.json
data/<namespace>/secret_notes/<path>.json
data/<namespace>/geode/drops/<path>.json
data/<namespace>/prize_ticket/rewards/<path>.json
data/<namespace>/mine_chest/rewards/<path>.json
```

钓鱼宝箱池是原版算法执行后的追加层，条目使用公共 Item Query；可限制普通/金色宝箱、出现概率、抽取次数、钓鱼等级和离岸距离。鱼塘定义按 `fish` 指定鱼种，并声明容量、繁殖时间、产物概率及扩容请求。
钓鱼宝箱规范定义和实际追加时遍历的池映射来自同一个目录快照；无效 reload 会保留
上一版定义与运行时池。

杀怪目标通过实体标签路由进度，`rewards` 使用公共 Action。博物馆奖励支持 `total_count`、`mineral_count`、`artifact_count` 和 `specific_items` 四类条件，奖励同样使用公共 Action。

怪物讨伐定义和按实体标签生成的进度路由同属一个不可变目录；无效候选会保留上一整版，
不会出现新目标读取旧标签索引。晶球定义与输入物品索引也按同一方式一次发布，重复输入
绑定不会改变当前活动目录。

普通秘密纸条使用完整资源路径作为 ID；本体旧数组格式继续兼容。定义、原版编号、
展示编号、排序列表和客户端同步 JSON 同属一个 revision，编号重复或不连续会拒绝
整个候选。失落之书同样把定义、世界交互点、解锁顺序和发现上限一次发布；交互点
冲突不会留下“新书配旧坐标”或“旧书配新坐标”的半套状态。

这些定义现在也进入统一内容图：钓鱼地点表为
`stardewcraft:fishing_pool`，鱼塘规则为 `stardewcraft:fish_pond_rule`，
博物馆里程碑为 `stardewcraft:museum_reward`，公会目标为
`stardewcraft:monster_slayer_goal`。旧字符串 ID 只在观察面映射到
`stardewcraft:legacy/<id>`，不会改写存档或数据包；新命名空间 ID 保持原值。
目录会解析鱼池的确定/随机渔获、鱼塘的精确鱼种/产物/扩容物品、博物馆的指定捐赠物
和奖励 Action，以及公会目标的奖励 Action。分类标签、旧条件字符串和怪物标签仍由
各自领域解释，不会被猜成物品或实体 ID。

### 运行时钓鱼地点与规则

数据包中的鱼池仍是主内容来源。只有地点取决于附属运行时区域或活动状态时，才使用 Java Provider：

```java
StardewFishingLocationKeys.register(MY_LOCATION_KEYS, 100, context -> {
    if (!isMyFishingRegion(context.level(), context.position())) return null;
    List<String> keys = new ArrayList<>(context.proposedKeys());
    keys.add("myaddon:festival_pool");
    return keys;
});
```

Provider 链式接收上一个结果，输出会去空白并按首次出现顺序去重；异常保留当前列表并继续。旧 `Beach`、`Forest` 等键继续可用，新池应使用 `namespace:path`。

需要玩家或活动状态的最终门禁使用 `StardewFishingRuleConditions`：

```java
StardewFishingRuleConditions.register(MY_FESTIVAL_GATE, 100,
    (context, proposed) ->
        context.rule().locations().contains("myaddon:festival_pool")
            && !isFestivalParticipant(context.player())
                ? StardewFishingRuleConditions.Decision.DENY
                : StardewFishingRuleConditions.Decision.PASS);
```

上下文提供只读 `StardewFishingRule` DTO、权威玩家/世界/浮标位置、Biome Holder 和魔法鱼饵状态。第一个 `ALLOW` 或 `DENY` 胜出；全部 `PASS` 使用本体条件结果。此钩子只改变当前规则资格，不自行发放鱼、不绕过候选概率、抓取上限或服务端收杆流程。

JEI 不应靠字符串包含关系猜测附属地点名称：

```java
StardewFishingLocationDisplays.register(MY_LOCATION_LABELS, 100, raw ->
    raw.equals("myaddon:festival_pool")
        ? Component.translatable("myaddon.jei.location.festival_pool")
        : null);
```

该 Provider 只返回客户端 `Component`，不参与服务端选鱼。地点池追加、节日参与门禁和 JEI 地点翻译是彼此独立的能力，附属可以只实现自己需要的一项；原有方法继续作为兼容入口。

服务端 reload 与客户端同步都会先构建完整的新钓鱼目录，再一次替换当前实例。地点规则
与可回收的同步 JSON 缓存始终由同一个目录实例提供；解析失败会保留上一实例。运行时
地点 Provider 和规则资格 Provider 是独立扩展注册，不属于 reload 状态，也不会被目录
替换清空。

鱼塘的静态鱼种、产物和扩容门槛继续由
`fishpond/pond_data/*.json` 定义。需要把自己的任务、成就或世界活动接到真实鱼塘
生命周期时，可以查询只读状态并监听服务端通知：

```java
List<StardewFishPondSnapshot> ponds =
    StardewFishPonds.all(serverLevel);

StardewFishPondEvents.registerDailyListener(
    id("pond_daily_progress"), 100,
    context -> observeDailyPond(
        context.absoluteDay(), context.pond()));

StardewFishPondEvents.registerRequestListener(
    id("pond_request_progress"), 100,
    context -> recordCompletedRequest(
        context.player(), context.requestedItem(),
        context.requestedCount(), context.pond()));
```

快照复制鱼种、人口、产物、请求、位置、所有者、天数和水色等持久状态，不公开可变
`FishPondRecord`。日结通知在本体完成该鱼塘本日计算后发送，不改变本体独立随机流；
请求通知在服务端真正消费最后一批所需物品并完成扩容后发送，其中
`requestedCount` 是本次完成请求所消费的最后一批数量。监听器按优先级和完整 ID
稳定排序，异常只隔离当前监听器。查询和通知都没有写权限；附属不能用它们绕过物品
消费、容量校验、经验奖励或存档标脏。

大型地图附属如果需要按具体坐标替换蚯蚓点掉落，可以注册
`StardewArtifactSpotDrops`。Provider 在核心地点和掉落组解析完成后执行，
返回 `null` 表示继续默认算法，返回空列表表示该点明确不掉落；非空堆栈会被
防御性复制。多个 Provider 按优先级降序、注册 ID 升序执行，首个非
`null` 结果生效，单个 Provider 的异常不会阻断后续 Provider。每个 Provider
获得按世界、位置、时间和 Provider ID 派生的独立随机流；返回 `null` 或抛出
异常不会消费核心掉落随机流，也不会改变其他 Provider 的随机结果。

```java
StardewArtifactSpotDrops.register(MY_ARTIFACT_SPOTS, 100, context ->
    isAddonArtifactZone(context.level(), context.position())
        ? List.of(new ItemStack(MyItems.OLD_COIN.get()))
        : null
);
```

若 Provider 会静态产出或依赖附属物品，可用第四参数声明内容引用；旧三参数重载保持
不变：

```java
StardewArtifactSpotDrops.register(MY_ARTIFACT_SPOTS, 100, provider,
    owner -> List.of(StardewContentReference.required(
        StardewContentReferenceRoles.DROP_ITEM,
        new StardewContentKey(
            StardewContentTypes.ITEM, MyItems.OLD_COIN_ID))));
```

`StardewArtifactSpotDrops.snapshot()` 返回 reload 后的不可变有效掉落组、规则 ID、
确定物品候选和 `dynamic` 标记，不执行随机数、玩家纸条/藏书选择或 Provider。
核心组进入 `stardewcraft:artifact_spot_pool` 内容类型，Provider 注册进入
`stardewcraft:artifact_spot_drop_provider`；因此服务器可以在没有实际挖掘方块时
检查地图地点、物品附属和运行时替换层是否完整。

遗失藏书不是 1.6 技能书，也不是背包物品。定义示例：

```json
{
  "unlock_at": 22,
  "text": "A literal text or a client translation key.",
  "available_when": [
    {"type": "stardewcraft:skill", "data": {"skill": "farming", "level": 2}}
  ],
  "interactions": [
    {
      "dimension": "stardewcraft:stardew_valley",
      "x": 170,
      "y": 40,
      "z": 51
    }
  ]
}
```

`unlock_at` 对应世界共享发现计数；阅读状态按玩家保存。`text` 可直接写正文，也可写资源包翻译键。内置调试入口：

```text
/stardew museum lostbooks status
/stardew museum lostbooks find
/stardew museum lostbooks set <count>
/stardew museum lostbooks read <namespace:path|0..20>
/stardew museum lostbooks reset_read
```

自定义晶球定义用 `inputs` 声明一个或多个已注册物品，用 `entries` 声明带 `weight` 的公共 Item Query。定义加载后，这些输入会同时被克林特界面和晶球破碎机识别；重复绑定同一输入会使整次候选 reload 失败。当前处理费用沿用原版固定 25 金，不开放客户端显示与服务端收费不一致的自定义费用。

兑奖定义的 `level` 从 0 开始；`repeat_every=0` 表示只匹配该次兑奖，正数表示从该次开始周期重复。原版 22 次后的九格循环也由这个字段表达。多个定义同时匹配时按 `priority` 从高到低、完整 ID 从小到大选择，条件不满足或 Item Query 无结果时继续尝试下一个定义；未配置的 level 会像原版空格一样被兑奖机跳过。
兑奖和普通矿井宝箱的规范定义与优先级排序表均一次发布，失败候选不会只替换其中一边。

普通矿井宝箱定义用 `floor` 指定层数。附属可以新增宝箱层，也可以用更高的 `priority` 覆盖同层低优先级奖励；奖励在玩家首次打开该层宝箱时由服务端稳定解析，并继续沿用每名玩家每层只领取一次的存档规则。220、320、420 层的骷髅矿井宝藏室仍使用独立随机池，不由这张普通层表接管。

### 扩展调用诊断（实验）

共享有序注册内核的运行时调用会累计有界诊断：调用次数、失败次数、超过 10ms 的
慢调用次数、总耗时、最大耗时和最近一次异常摘要。异常摘要只保存异常类型、短消息
和时间，不保存无限增长的调用历史，也不会把堆栈同步给客户端。

```text
/stardew debug extensions
/stardew debug extensions explain stardewcraft:combat/damage_modifiers
```

`StardewExtensions.find(...)` 返回同一份只读快照，便于测试和管理集成定位排序与故障。
诊断计数不会改变 Provider 的 `PASS/ALLOW/DENY`、异常隔离或领域回退语义；只有通过
共享调用入口的扩展点才产生运行时指标，剩余旧注册表会在迁入共享内核时逐步覆盖。

### 网络能力协商（实验）

现有网络协议版本仍然严格匹配，不修改或复用任何旧 payload ID。Java 附属可以在
模组初始化期间额外声明版本化能力：

```java
StardewNetworkCapabilities.register(
        ResourceLocation.fromNamespaceAndPath("example", "catalog_display"),
        1,
        StardewNetworkCapabilityRequirement.OPTIONAL);
```

`OPTIONAL` 能力缺失时连接继续，调用
`StardewNetworkCapabilities.supports(connection, id)` 决定是否发送对应展示数据；
服务端权威逻辑不能依赖客户端声称支持某项能力。`REQUIRED_REMOTE` 要求远端存在
相同 ID 和版本，否则在配置阶段以可读原因拒绝连接。每端最多声明 256 项，握手
快照不可变且按完整 ID 稳定排序。协商 payload 自身是可选通道，因此同一旧协议
中尚未实现能力协商的客户端仍可连接未声明必需客户端能力的服务端；一旦服务端
附属注册 `REQUIRED_REMOTE`，缺少协商通道的旧客户端也会在配置阶段明确被拒绝。

## 命名空间与加载顺序

- 所有第三方 ID 必须使用附属自己的命名空间，例如 `myaddon:rainy_reward`。
- Java 类型和 Provider 遇到重复 ID 会立即抛出异常。
- 附属的 `neoforge.mods.toml` 应声明对 `stardewcraft` 的必需依赖，并设置 `ordering="AFTER"`。
- 注册应在附属 Mod 构造阶段完成，不要在 `/reload` 时重复注册 Java 类型。

完整代码见 [`examples/stardewcraft-addon`](../examples/stardewcraft-addon)。

## 物品 Data Map

固定资源路径：

```text
data/stardewcraft/data_maps/item/stardew_item_data.json
```

示例：

```json
{
  "replace": false,
  "values": {
    "myaddon:blueberry": {
      "category": "myaddon:crop",
      "base_sell_price": 50,
      "edibility": 10,
      "energy": 25,
      "health": 11,
      "hidden": false
    },
    "#c:gems": {
      "category": "stardewcraft:mineral",
      "base_sell_price": 80
    }
  }
}
```

解析优先级固定为：

1. 动态 Provider，优先级较大的先执行。
2. 同优先级 Provider 按完整 ID 排序。
3. 同步 Data Map。
4. 本体旧 `IStardewItem` 兼容层。

`base_sell_price=-1` 表示不可出售。Provider 返回 `Optional.empty()` 表示不处理该物品，让后续来源继续解析。

`edibility > -300`，或非零的 `energy` / `health`，会把目标识别为星露谷食物。目标物品仍必须自带 Minecraft Food Component；Data Map 只接入行为，不会为普通材料合成食用动画、时长或容器规则。在星露谷主维度和矿井维度中，配置后的原版或第三方食物即使原版饥饿值已满也能食用；原物品的 Buff、食用动画和容器返还照常执行，完成后再按 `energy` / `health` 结算星露谷属性。本体 `IStardewItem` 继续使用自身结算，兼容层不会重复恢复。

`hidden` 在 0.5.x 仍是预留并同步的元数据，不会自行改变物品目录或 JEI 可见性；需要隐藏物品时请使用 `stardewcraft:hidden` 物品标签。

### 食物 Buff Data Map

不要把 Buff 写进 `stardew_item_data`。独立的同步 Data Map 路径是：

```text
data/stardewcraft/data_maps/item/stardew_food_effects.json
```

它可以给任意已有 Minecraft 食物追加 Minecraft、本体或附属注册的 MobEffect：

```json
{
  "replace": false,
  "values": {
    "minecraft:golden_carrot": {
      "effects": {
        "myaddon:golden_luck": {
          "effect": "stardewcraft:spirit_blessing",
          "duration_ticks": 1200,
          "amplifier": 0,
          "chance": 1.0,
          "ambient": false,
          "show_particles": false,
          "show_icon": true
        }
      }
    }
  }
}
```

`effects` 的键是稳定条目 ID。不同数据包提供不同条目时会组合；同 ID 由高优先级
数据包覆盖，因此附属不必复制另一附属的完整效果列表。`duration_ticks` 必须大于零，
`amplifier` 为零起始，`chance` 范围为 `0..1`，其余显示字段均可省略。

效果只在服务端确认完成食用后追加，所以原物品的效果、动画、取消处理和容器返还均
保持原样。只配置效果、不配置 `stardew_item_data` 的食物也能工作；在星露谷主维度
和矿井维度，它还可以在原版饥饿值已满时食用。`/reload` 只改变之后的食用，已经生效
的 MobEffect 会按原持续时间自然结束。

## 动态物品 Provider

```java
StardewItemDataApi.registerProvider(
    ResourceLocation.fromNamespaceAndPath("myaddon", "quality_gem"),
    100,
    stack -> {
        if (!stack.is(MyItems.GEM.get())) {
            return Optional.empty();
        }
        return Optional.of(new StardewItemData(
            ResourceLocation.fromNamespaceAndPath("myaddon", "gem"),
            500, -300, 0, 0, false
        ));
    }
);
```

Provider 适合 NBT/Data Component、品质或其它堆栈状态会改变元数据的情况。静态属性应优先使用数据包。

公共元数据当前参与出售与出货价格、职业加成、背包整理、礼物判定、博物馆捐赠、鱼塘、钓鱼、机器输入、节日陈列、目录与标准 tooltip。附属物品无需实现本体的 `IStardewItem`；该接口只作为旧本体物品的兼容来源。

## 统一获得来源（实验）

`StardewAcquisitionSources.find(stack[, player])` 返回同一物品的不可变来源列表。
本体当前自动投影静态商店条目、合成、烹饪和固定输出的机器配方。每条来源包含
物品 ID、`SHOP / CRAFTING / COOKING / MACHINE / LOOT / QUEST / FESTIVAL /
OTHER` 类型、稳定来源 ID、产出数量、展示 Component，以及是否仍需运行时条件
判断的标记。它只描述“哪里可能获得”，不会绕过商店条件、配方解锁、机器输入或
服务端奖励事务。

动态商店、NBT 产出、随机掉落、任务与节日奖励由拥有真实上下文的附属追加：

```java
StardewAcquisitionSources.register(
    ResourceLocation.fromNamespaceAndPath("myaddon", "moon_apple"),
    100,
    context -> context.targetItemId().equals(MOON_APPLE_ID)
        ? List.of(new StardewAcquisitionSource(
            MOON_APPLE_ID,
            StardewAcquisitionSource.Kind.FESTIVAL,
            ResourceLocation.fromNamespaceAndPath(
                "myaddon", "moon_festival_reward"),
            1,
            Component.translatable(
                "myaddon.acquisition.moon_festival"),
            true
        ))
        : List.of()
);
```

Provider 按优先级、完整注册 ID 排序；相同 `kind + sourceId` 保留先到者。异常、
null、目标物品不匹配的结果只丢弃当前来源。查询栈和展示 Component 均防御性复制，
一个附属不能通过修改 DTO 污染后续 Provider。动态产出不会被核心猜成静态来源。
该目录尚未冻结为客户端 UI 协议；后续图鉴、JEI/Jade 和获得来源页应消费它，而
不是再次扫描各自的数据表。

## 通用货币与组合成本（实验）

`StardewCurrencies` 是货币元数据与服务端余额的统一目录。本体金币和展会星星币
分别使用 `stardewcraft:money` 与 `stardewcraft:fair_star_tokens`。附属登记货币时
必须提供命名空间 ID、显示名、图标、余额上限，以及只操作传入玩家账户的同步
Handler：

```java
ResourceLocation marks = id("orchard_marks");
StardewCurrencies.register(
    new StardewCurrency(
        marks,
        Component.literal("Orchard Marks"),
        new ItemStack(Items.EXPERIENCE_BOTTLE),
        21863L),
    new StardewCurrencyHandler() {
        public long balance(ServerPlayer player) {
            return player.experienceLevel;
        }

        public boolean withdraw(ServerPlayer player, long amount) {
            if (amount > player.experienceLevel) return false;
            player.giveExperienceLevels(-(int) amount);
            return true;
        }

        public boolean deposit(ServerPlayer player, long amount) {
            if (amount > 21863L - player.experienceLevel) return false;
            player.giveExperienceLevels((int) amount);
            return true;
        }
    });
```

Handler 的 `withdraw` 和 `deposit` 必须是精确、同步、可互相逆转的操作。核心会在
调用前后验证余额和上限；返回值、异常或实际余额不一致时会拒绝本次操作，并尝试
恢复调用前余额。自定义货币的持久化与客户端同步仍由拥有该货币的附属负责；目录
不会替附属猜测存档作用域。

`StardewCost` 可以组合任意数量的 `StardewCurrencyCost` 与
`StardewItemCost`。所有组件先整体预检，再按确定顺序扣除；中途失败会逆序回滚。
成功结果携带一次性的 `StardewPaymentReceipt`，奖励在支付后失败时可以退款：

```java
StardewPaymentResult payment = StardewCosts.pay(
    player,
    StardewCost.of(
        new StardewCurrencyCost(marks, 20),
        new StardewItemCost(
            ResourceLocation.parse("minecraft:apple"), 3)));

if (!payment.success()) {
    return StardewActionResult.failure(payment.failureReason());
}
if (!grantReward(player)) {
    payment.receipt().orElseThrow().refund();
    return StardewActionResult.failure("reward_failed");
}
```

菜单、诊断或附属服务在执行前可以读取同一份组合费用的逐项报告：

```java
StardewRequirementReport affordability =
    StardewCosts.requirements(player, cost);
```

报告会先按支付规则合并相同货币和物品组件，再逐项返回 `COST_CURRENCY` 或
`COST_ITEM`；缺少货币 Handler、未知物品或金额溢出使用 `ERROR`，余额不足使用
`UNSATISFIED`。该调用不扣除任何内容，只是当前 tick 的只读快照；即使
`satisfied()` 为 true，真正操作仍必须调用 `pay`，以处理余额在两次调用之间变化的
情况。

物品退款保存被消费堆栈的 Data Components；背包放不下时会把原堆栈退到玩家脚下。
普通商店的金币加交换物、铁匠工具升级、展会星币商店和金币兑换星币已迁入同一
事务实现，旧 `price`、`tradeItem`、商店 ID 和网络包不变。

这一层目前仍是实验能力。标准商店已能通过独立的 `shop_costs` 数据规则或 Java
Provider 使用任意组合成本，客户端会按服务器返回的有界成本快照显示余额并计算
可购买数量；全局 HUD 和其它专用购买界面仍未通用化。旧 `price` 永远继续表示
金币，不会因附属注册货币而改变含义。

矿区通用方块分类使用以下可扩展标签：

| 方块标签 | 含义 |
| --- | --- |
| `stardewcraft:stardew_stones` | 星露谷矿区石头与可破坏岩块 |
| `stardewcraft:stardew_ores` | 参与矿石通用流程的矿石块 |
| `stardewcraft:stardew_minerals` | 地面矿物与宝石矿块 |
| `stardewcraft:iridium_ores` | 需要触发铱矿额外碎片规则的矿石块 |

这些标签只负责分类，不会根据注册名推断掉落物或经验。自定义矿石的独立掉落映射仍需要矿井内容 API。

## Condition

注册：

```java
StardewConditions.register(MY_ID, MyCondition.CODEC,
    (context, data) -> context.player() != null && data.test(context.player()));
```

统一 Codec 格式：

```json
{
  "type": "myaddon:my_condition",
  "data": {
    "value": 1
  }
}
```

当前剧情前置条件仍兼容旧的扁平格式。自定义类型在剧情中写成：

```json
{
  "type": "myaddon:my_condition",
  "value": 1
}
```

未知类型、无效字段或执行异常都按失败处理，不会默认放行。

内置类型：

| 类型 | 数据 |
| --- | --- |
| `stardewcraft:always` | `value: boolean`，默认 `true` |
| `stardewcraft:has_item` | `item`、`count` |
| `stardewcraft:money` | `min`、`max` |
| `stardewcraft:flag` | `id`、`present` |
| `stardewcraft:skill` | `skill`、`level`；要求技能达到指定等级 |
| `stardewcraft:season` | `seasons`；可选 `spring`、`summer`、`fall`、`winter` |
| `stardewcraft:time` | `start`、`end`；HHMM 整数，起点包含、终点不包含，默认 `0000-2600` |
| `stardewcraft:seen_event` | `id`；要求当前玩家已经看过该服务端剧情事件 |
| `stardewcraft:location` | 可组合 `locations`、`required_tags`、`excluded_tags` 和 `properties` |

`stardewcraft:time` 直接读取服务端 Stardew 时钟，允许 `0000` 至 `2600`，分钟
必须小于 60。`start > end` 表示跨午夜窗口，例如 `2200-0200`；两者相等表示全天。
它可以与地点、季节、旗标等 Condition 组合成商店营业时间、NPC 服务、任务或
商品可用窗口，不需要消费方各自转换 Minecraft `dayTime`。

`stardewcraft:location` 使用服务端玩家的最具体逻辑地点。`locations` 中任一地点
匹配即可，并自动接受它的子地点；其余三组条件同时成立才通过。标签和属性来自
解析后的地点环境，因此会包含父地点继承值和子地点覆盖值：

```json
{
  "type": "stardewcraft:location",
  "data": {
    "locations": ["myaddon:orchard"],
    "required_tags": ["stardewcraft:outdoor"],
    "excluded_tags": ["myaddon:closed"],
    "properties": {
      "myaddon:primary_fruit": "apple"
    }
  }
}
```

该 Condition 可直接用于商店/商品、邮件、任务、剧情、掉落、采集等已经支持
`available_when` 的玩家上下文。它不能放进节日定义自身的世界级
`available_when`；节日地点门禁继续使用 `world.location`，避免用某个玩家状态
决定全服日历是否存在。

### 可查询要求与锁定说明（实验）

`StardewRequirements.evaluateAll(context, conditions)` 会对同一组权威 Condition
逐项求值，返回保持声明顺序的 `StardewRequirementReport`。每一行区分
`SATISFIED`、`UNSATISFIED`、`ERROR`，报告可直接查询 `satisfied()` 与
`blocking()`。它不采用“遇到第一个失败就停止”的 UI 语义，因此菜单、任务面板
和诊断页可以一次展示全部阻断条件。

```java
StardewRequirementReport report = StardewRequirements.evaluateAll(
    StardewConditionContext.forPlayer(player),
    definition.availableWhen());
```

内置 Condition 会提供物品、金钱、剧情旗标、技能、季节、时间、事件和地点的
基础说明。自定义 Condition 可注册有序 Provider，补充自己的展示文本：

```java
StardewRequirements.register(MY_DISPLAY_ID, 100,
    (context, condition, proposed) ->
        condition.type().equals(MY_CONDITION_ID)
            ? new StardewRequirement(
                condition.type(),
                proposed.state(),
                Component.translatable("myaddon.requirement.player_named"),
                true)
            : null);
```

Provider 只能替换说明，不能修改 Condition 类型或服务端求值结果；单个 Provider
异常会被隔离。`specific=false` 表示当前只有类型 ID 级别的保底说明，调用方可选择
显示通用“额外条件”而不是暴露内部 ID。

系统适配器也可以把不属于 Condition 的权威事实投影为同一种报告。首个适配器
`StardewFestivalRewards.requirements(player, festivalId, rewardId)` 会逐项报告
节日是否存在、会话是否开放、玩家是否参与以及奖励是否尚未领取；其稳定类型定义
在 `StardewRequirementTypes`。领取事务和这份报告共用同一份 preflight 状态，
避免 UI 复制一套容易漂移的判断。

报告只覆盖它列出的已知前置事实。即使 `satisfied()` 为 true，节日奖励 Handler
仍可能基于小游戏成绩、背包容量或附属私有状态返回拒绝；商店库存、任务是否已接受
等尚未提供系统适配器的规则也不会被虚构成已满足。客户端显示的报告永远不能作为
购买、接受或领取授权，实际操作仍必须调用对应服务端事务。

## Item Query

注册：

```java
StardewItemQueries.register(MY_ID, MyQuery.CODEC,
    (context, data) -> List.of(new ItemStack(data.item(), data.count())));
```

解析器必须返回非空 `List<ItemStack>`；框架会过滤空堆栈并复制结果。随机选择必须使用 `StardewItemQueryContext.random()`，不要自行创建不可复现的随机源。

如果自定义查询的强类型 payload 保存了确定的内容 ID，可使用可选第四参数把引用交给统一目录。旧三参数重载保持不变：

```java
StardewItemQueries.register(MY_ID, MyQuery.CODEC,
    (context, data) -> List.of(new ItemStack(data.item(), data.count())),
    (owner, data) -> List.of(
        StardewContentReference.required(
            StardewContentReferenceRoles.QUERY_ITEM,
            new StardewContentKey(
                StardewContentTypes.ITEM,
                data.itemId()))));
```

内置 `item`、`one_of`、`random_count`、`one_of_queries` 和 `weighted` 查询会递归提取确定物品引用；标签查询保持动态，不会把标签成员固化进目录。

内置类型：

| 类型 | 数据 |
| --- | --- |
| `stardewcraft:item` | `item`、`count` |
| `stardewcraft:random_tag` | `tag`、`count` |
| `stardewcraft:one_of` | `items`、`count` |
| `stardewcraft:one_of_queries` | `queries`；等概率执行其中一条完整 Item Query |
| `stardewcraft:random_count` | `query`、`min_count`、`max_count`；随机覆盖结果数量 |

## Action

注册：

```java
StardewActions.register(MY_ID, MyAction.CODEC, (context, data) -> {
    data.apply(context.player());
    return StardewActionResult.ok();
});
```

Action 只在服务端执行。业务条件不满足时返回 `StardewActionResult.failure(message)`；不要把客户端发来的任意字符串直接当作可信 Action。

内置类型：

| 类型 | 数据 |
| --- | --- |
| `stardewcraft:set_flag` | `id` |
| `stardewcraft:add_money` | `amount` |
| `stardewcraft:add_item` | `item`、`count` |
| `stardewcraft:remove_item` | `item`、`count` |
| `stardewcraft:start_quest` | `quest` |
| `stardewcraft:remove_quest` | `quest` |
| `stardewcraft:apply_unlock_source` | `source`；应用一条命名空间解锁来源 |

剧情触发的状态 Action 还会额外校验服务端生成的 `sessionId`、事件 ID、原始命令序号、动作类型和参数，并拒绝重放。

## 任务定义

### 统一进度状态与生命周期

任务、特殊订单、邮件、社区中心、博物馆和节日会话保留各自权威存档与专用 API，但现在同时
投影为统一的只读进度快照。该层不把这些系统压成一种万能任务格式，也不会迁移或
重写旧存档：

```java
StardewProgressSnapshot quest = StardewProgress.inspect(
    player,
    new StardewProgressKey(
        StardewProgressDomains.QUEST,
        ResourceLocation.parse("myaddon:story/first")
    )
);
```

`StardewProgressKey` 由“进度领域 + 内容 ID”组成。本体领域包括
`stardewcraft:quest`、`stardewcraft:special_order`、`stardewcraft:mail`、
`stardewcraft:community_center`、`stardewcraft:museum` 和
`stardewcraft:festival`。
快照统一提供：

- `PLAYER / FARM / TEAM / WORLD` 所有权范围；
- `NOT_STARTED / AVAILABLE / SCHEDULED / ACTIVE / REWARD_AVAILABLE /
  COMPLETED / FAILED / EXPIRED / CANCELLED / UNAVAILABLE` 阶段；
- 零到多个带稳定 ID 的数值目标；
- 定义是否仍存在、当前玩家是否可领奖、剩余天数。

菜单在显示“接受”或“领取”按钮前，可请求统一、只读的操作说明：

```java
StardewRequirementReport accept =
    StardewProgressRequirements.requirements(
        player, quest.key(), StardewProgressOperation.ACCEPT);
StardewRequirementReport claim =
    StardewProgressRequirements.requirements(
        player, quest.key(), StardewProgressOperation.CLAIM_REWARD);
```

普通任务接受会报告定义、是否已在任务日志以及定义的全部 `available_when`；
特殊订单接受会额外报告看板解锁、当前轮次/活动订单名额和看板是否实际提供该订单；
领取统一报告 `rewardClaimable`。普通任务、特殊订单的服务端接受与领取入口已消费
同一报告，因此说明与操作不会各维护一份判断。对附属自有进度域，核心采用保守的
通用语义：只有 `AVAILABLE` 可接受，只有 `rewardClaimable=true` 可领取。这个
facade 不会替附属执行操作或猜测存档；附属仍在自己的服务端 Action/网络入口修改
状态，并在执行时重新验证。

普通任务投影为玩家进度，特殊订单投影为团队进度，邮件依次经历
`NOT_STARTED -> SCHEDULED -> AVAILABLE -> COMPLETED`。数据包定义临时消失时，
活动中的数据驱动任务投影为 `UNAVAILABLE`，不会删除其已保存目标状态。

社区中心继续使用旧存档中的数字 bundle/area ID；不要自行拼接内部路径，使用
`StardewProgress.communityCenterBundle(bundleId)` 和
`StardewProgress.communityCenterArea(areaId)` 取得规范 Key。Bundle 快照提供
已填槽位/要求槽位、是否完成和是否可领奖；区域快照提供已完成 bundle 数。玩家变体
目录仍由现有 Community Center API 决定，因此同一个数字 ID 会按当前玩家的活动
目录解释。

博物馆提供一个聚合收藏 Key 和每个奖励里程碑的独立 Key：

```java
StardewProgressSnapshot collection = StardewProgress.inspect(
    player, StardewProgress.museumCollection());
StardewProgressSnapshot milestone = StardewProgress.inspect(
    player, StardewProgress.museumReward("myaddon:deep_minerals"));
```

聚合快照发布总捐赠、矿物和古物计数；奖励快照按 `total_count`、
`mineral_count`、`artifact_count` 或 `specific_items` 发布自己的目标。奖励定义
被数据包移除时不会改写博物馆存档。

节日领域按规范 festival ID 投影当前或最近一次持久会话，范围为 `WORLD`：

```java
StardewProgressKey festivalKey = StardewProgress.festival(
    ResourceLocation.parse("myaddon:apple_day"));
StardewProgressSnapshot session =
    StardewProgress.inspect(player, festivalKey);
```

没有会话的已知定义为 `NOT_STARTED`；`SCHEDULED/PREPARING_MAP` 为
`SCHEDULED`，`OPEN` 为 `AVAILABLE`，`MAIN_EVENT/ENDING/RESTORING_MAP` 为
`ACTIVE`，`CLOSED` 为 `COMPLETED`。阶段提交后会发布统一进度事件，世界阶段变化
不伪造玩家 actor。参与者加入/离开、地图恢复细节仍由节日专用生命周期 API 提供；
Handler 自有奖励 ID 只有在显式声明目录后才会进入通用目标，不扫描私有字段或猜测
小游戏实现。

Activity 使用 `StardewFestivalActivities.progressDomain/progressKey` 保留
festival/activity 复合身份。寻蛋已接入首个玩家级目标；附属可用同一规则为自己的
小游戏注册标准进度 Provider，统一枚举、监听和展示，不需要让核心认识它的分数类。

显式注册的节日奖励使用
`StardewFestivalRewards.progressDomain/progressKey` 保留 festival/reward 复合
身份，并自动进入稳定枚举、统一奖励预览和玩家级进度。目录只报告已知状态，不替代
领取 Handler：开放且参与的未领取奖励为 `AVAILABLE`，成功领取为 `COMPLETED`，
会话关闭后未领取为 `EXPIRED`；`rewardClaimable` 始终为 false，避免把展示元数据
误当作服务端授权。

附属自己的系统可以注册完全不同的进度领域：

```java
ResourceLocation domain = ResourceLocation.parse("myaddon:orchard_trial");
StardewProgress.registerProvider(
    ResourceLocation.parse("myaddon:orchard_progress"),
    100,
    domain,
    (player, entryId) -> entryId.equals(ResourceLocation.parse("myaddon:first_harvest"))
        ? new StardewProgressSnapshot(
            new StardewProgressKey(domain, entryId),
            StardewProgressScope.PLAYER,
            StardewProgressPhase.ACTIVE,
            List.of(new StardewProgressMetric(
                ResourceLocation.parse("myaddon:apples"), 2, 5)),
            true, false, OptionalInt.empty())
        : null
);
```

Provider 只负责读取自己拥有的状态。它不需要继承 `StardewQuest`，核心也不会猜测
附属的持久化格式。Provider 按优先级和注册 ID 稳定排序，异常会被隔离，返回的 Key
必须与请求完全一致。若希望通用菜单显示“可接受”，应投影 `AVAILABLE`；希望显示
“可领奖”，应投影 `REWARD_AVAILABLE` 且令 `rewardClaimable=true`，但这些状态
仍不是客户端执行权限。

需要进入菜单、图鉴或诊断目录的进度项，由 Provider 覆盖 `entries(player)` 广告；
只支持已知 Key 直查的 Provider 可以保留默认空集合。领域目录会合并所有 Provider，
按完整 ID 稳定排序、去重，并再次通过权威 `inspect` 生成快照：

```java
List<StardewProgressSnapshot> museumEntries = StardewProgress.list(
    player, StardewProgressDomains.MUSEUM);
```

五个本体领域都提供目录：任务包含活动/已完成/当前定义，特殊订单包含看板与活动项，
邮件包含定义和当前待投递项，社区中心包含当前玩家变体目录中的 bundle/区域，博物馆
包含聚合收藏和所有数据包奖励里程碑。目录是服务端只读视图，不赋予客户端修改状态
的权限。

### 统一奖励预览

进度快照只回答阶段和目标；奖励展示通过独立的只读预览查询，绝不执行奖励：

```java
StardewRewardPreview preview = StardewRewardPreviews.preview(player, progressKey);
```

`StardewRewardComponent` 统一描述 `ITEM / CURRENCY / ACTION / OTHER`，包含稳定 ID、
数量、复制后的图标和 `Component` 文本。`runtimeDependent=true` 表示实际领取结果
还会受当前玩家、resolver 或服务端 Action 影响；`StardewRewardPreview.exhaustive`
表示当前 Provider 是否认为全部奖励分量都已描述。展示层必须把它当提示，不能据此
发物品、加钱或跳过原系统校验。

本体适配覆盖：

- 任务的金钱、奖励说明和 `on_complete` Action；
- 邮件附件、金钱、配方、后续任务/订单和交付/阅读 Action；
- 特殊订单的金钱、友情、邮件和附属奖励类型；
- 社区中心 bundle 的静态奖励（标记为可能被 resolver 改写）；
- 博物馆里程碑的标准物品和其它 Action。

附属可以按优先级组合或替换预览；返回 `null` 保留当前 proposed 值，异常会隔离：

```java
StardewRewardPreviews.register(
    ResourceLocation.parse("myaddon:orchard_rewards"),
    100,
    (player, progress, proposed) -> progress.equals(orchardKey)
        ? new StardewRewardPreview(
            progress,
            List.of(new StardewRewardComponent(
                StardewRewardComponent.Kind.ITEM,
                ResourceLocation.parse("minecraft:apple"),
                3,
                new ItemStack(Items.APPLE, 3),
                Component.literal("3 Apples"),
                false)),
            true)
        : null
);
```

统一事件在权威状态已经提交后广播，不能取消原操作：

```java
StardewProgressEvents.register(
    ResourceLocation.parse("myaddon:progress_listener"),
    100,
    event -> recordForAddonStatistics(
        event.type(), event.after(), event.cause(), event.actor())
);
```

真实任务接受/推进/完成/领奖/取消/过期，特殊订单接受/目标推进/可领奖/领奖/失败，
邮件排期/入箱/阅读、社区中心捐献/完成/领奖，以及博物馆捐赠/里程碑/领奖都会进入
同一事件流。事件带服务端世界、可选玩家 UUID、变更前后快照和稳定 cause ID；
监听器异常不会阻断后续监听器或回滚已经完成的游戏操作。附属领域也可以用
`StardewProgressEvents.announce` 发布同一格式的已提交事实。

邮件的静态物品附件、社区中心静态奖励，以及博物馆奖励中的标准
`stardewcraft:add_item` Action 会自动投影为
`StardewAcquisitionSource.Kind.PROGRESS`，因此图鉴/JEI 等统一来源查询无需逐条
硬编码。运行时 Action、自定义奖励 resolver、特殊订单动态奖励等无法静态确定的
产物，仍由拥有真实上下文的附属通过 `StardewAcquisitionSources` Provider 补充。

每个现代任务占一个 JSON 文件：

```text
data/<namespace>/quests/<path>.json
```

文件路径就是任务 ID。例如 `data/myaddon/quests/story/first.json` 对应 `myaddon:story/first`。

```json
{
  "title": {"literal": "First Harvest"},
  "description": {"literal": "Bring in one apple."},
  "objective_text": {"literal": "Obtain an apple"},
  "objective": {
    "type": "stardewcraft:item_harvest",
    "data": {"item": "minecraft:apple", "count": 1}
  },
  "available_when": [
    {"type": "stardewcraft:always", "data": {"value": true}}
  ],
  "on_complete": [
    {
      "type": "stardewcraft:start_quest",
      "data": {"quest": "myaddon:story/second"}
    }
  ],
  "money_reward": 100,
  "can_cancel": true,
  "days": -1
}
```

任务定义是不可变数据，玩家存档只保存 `DefinitionId`、接受/完成状态、倒计时和目标进度。定义临时消失时，任务会显示为不可用且允许取消；定义恢复后可重新绑定。旧数字 ID 会解析为 `stardewcraft:<id>`，旧完整任务 NBT 仍可读取。

内置目标类型：

| 类型 | 主要数据 |
| --- | --- |
| `stardewcraft:basic` | 无；由剧情、交互或 Action 完成 |
| `stardewcraft:item_harvest` | `item`、`count` |
| `stardewcraft:item_delivery` | `target_npc`、`item`、`count`、`target_message`、`friendship` |
| `stardewcraft:crafting` | `recipe` |
| `stardewcraft:monster` | `monster`、`count`、`target_npc` |
| `stardewcraft:socialize` | 可选 `npcs`、`friendship` |
| `stardewcraft:location` | `location`；矿层使用 `MineFloor:<层数>` |
| `stardewcraft:fishing` | `item`、`count`、`target_npc` |
| `stardewcraft:building` | `building` |
| `stardewcraft:resource` | `item`、`count`、`target_npc` |

附属注册目标：

```java
StardewQuestObjectives.register(MY_OBJECTIVE_ID, MyObjective.CODEC,
    definition -> new MyObjectiveRuntime(definition));
```

`QuestObjectiveRuntime` 接收稳定的 `QuestProgressEvent`，并负责 `saveState/loadState`。完整实现见示例附属的 `break_targets`。

日常委托配置位于：

```text
data/stardewcraft/daily_quest_pools/default.json
```

数据包可以按正常优先级覆盖概率阈值、持续时间、NPC、四季交付物/鱼、资源和怪物池。

## 商店

商店定义路径：

```text
data/<namespace>/shops/<path>.json
```

```json
{
  "owner_npc": "pierre",
  "owner_dialogue": "myaddon.shop.apple_stand",
  "entries": [
    {
      "item": "minecraft:apple",
      "price": 75,
      "stock": 5,
      "seasons": [0, 1],
      "available_when": [
        {"type": "stardewcraft:always", "data": {"value": true}}
      ]
    },
    {
      "item": "minecraft:golden_apple",
      "price": 0,
      "trade_item": "minecraft:emerald",
      "trade_item_count": 3,
      "stock": 1
    }
  ],
  "accepted_sell_types": [],
  "inventory_providers": ["myaddon:daily_stock"]
}
```

`price` 是金币价格；`trade_item` 和 `trade_item_count` 表示物品交换，可以与金币价格同时存在。`stock`、`min_year`、`min_mine_level`、`mail_flag`、`day_of_week`、`day_of_month_parity`、`purchase_stack` 和 `available_when` 都在服务端重新校验。

动态库存 Provider：

```java
StardewShopInventoryProviders.register(MY_PROVIDER_ID, context -> List.of(
    new StardewShopEntry(/* ... */)
));
```

Provider 每次打开商店和处理购买时都会重新生成库存，必须对同一上下文给出稳定顺序。
服务端菜单、诊断和附属集成不应把当前数组下标当作内容身份；使用运行时目录：

```java
StardewShopRowKey rowKey = new StardewShopRowKey(
    "myaddon:orchard_stand", "myaddon:orchard_blessing");
Optional<StardewShopInventorySnapshot> row =
    StardewShopInventories.inspect(player, rowKey);
List<StardewShopInventorySnapshot> catalog =
    StardewShopInventories.candidates(
        player, "myaddon:orchard_stand");
StardewRequirementReport stock =
    StardewShopInventories.requirements(player, rowKey, 3);
```

`StardewShopRowKey` 保留 shop 和 entry 两段原始身份，兼容旧字符串商店 ID、命名空间
商店 ID、真实物品 ID 和虚拟商品 ID。`list` 表示当前实际上架的运行时行，并保留
剩余库存为 0 的行以便报告 `SHOP_STOCK_AVAILABLE`；正常开店和购买仍过滤售罄行。
`candidates` 是更宽的候选目录：数据包声明和动态 Provider 提供的条目即使因为日期、
`available_when`、矿井层数、邮件、博物馆、剧情或“已经拥有”而暂时不上架，也会保留
并给出逐项阻断原因。`inspect` 与 `requirements` 按候选目录查询，因此可区分“条目不
存在”和“条目存在但当前锁定”。两层目录与开店过滤共用同一个服务端评估器，而不是
由附属或 UI 复制一份判断。当天才生成的随机库存也会进入候选目录，但生成器没有发布
的其他日期候选不会被核心猜测出来。

同一商店不得发布重复 entry ID：这在旧购买协议中本来就无法无歧义回查。目录会记录
冲突并保留第一行，与当前服务端购买回退规则一致。附属需要多个外观相同但价格或行为
不同的商品时，应给它们不同的虚拟 entry ID，并由商品 Handler 决定实际交付。
旧 `OpenShopScreenPayload`、`ShopPurchasePayload(itemIndex, itemId)` 和客户端界面
没有修改；数组下标只继续作为旧 UI 的位置提示，服务端仍以稳定 entry ID 重新查找。

任意货币或多种交换物不要塞入旧 `price/trade_item` 字段，而是添加独立规则：

```text
data/<namespace>/shop_costs/<path>.json
```

```json
{
  "shop": "myaddon:orchard_stand",
  "item": "minecraft:apple",
  "priority": 100,
  "currencies": [
    {"id": "myaddon:orchard_marks", "amount": 2}
  ],
  "items": [
    {"id": "minecraft:emerald", "amount": 1}
  ],
  "available_when": []
}
```

规则的 `shop` 必须与打开和购买时使用的商店 ID 完全一致，`item` 匹配商店行的
稳定物品/虚拟商品 ID。最高优先级的可用规则完整替换该行的旧成本；同优先级按规则
资源 ID 排序。金额是一次购买的单位成本，服务端按实际数量安全放大，并在打开、
成本快照请求和购买时重新解析同一动态库存。

需要玩家状态之外的动态算法时使用有序 Java Provider：

```java
StardewShopCosts.register(id("seasonal_cost"), 100,
    (context, proposed) -> {
        if (!context.shopId().equals("myaddon:orchard_stand")
                || !context.entry().item().equals("minecraft:apple")) {
            return proposed;
        }
        return StardewCost.of(new StardewCurrencyCost(
            id("orchard_marks"), 2L * context.quantity()));
    });
```

Provider 接收数据规则或旧字段生成的前序成本，返回新的不可变成本。异常或 `null`
只拒绝当前 Provider，不会破坏后续 Provider 或默认价格。客户端不自行执行
Provider：商店打开后会请求只包含被覆盖行的成本、显示元数据和当前可用余额；购买
仍由服务端重建库存、重算成本并执行原子支付。旧 `OpenShopScreenPayload` 和
`ShopPurchasePayload` wire 字段未修改。

服务端菜单或诊断可调用
`StardewShopCosts.requirements(context, defaultCost)`。它会先运行同一组有序成本
Provider，再把最终组合费用交给通用 affordability 报告，因此附属货币和交换物不会
退回旧金币说明。行是否仍在候选/实际上架目录、剩余库存以及虚拟商品 Handler 是否
接受，则由 `StardewShopInventories.requirements` 合并报告；费用和行状态都只是
购买前说明，实际购买事务仍会重新验证，客户端不得据此直接发货。

商店行也可以表示配方、解锁、治疗、传送等不生成 `ItemStack` 的虚拟商品。
这类行仍使用稳定的命名空间 `item` 作为商品 ID、使用同一套 `shop_costs` 和库存
字段。纯数据包可以把一个已注册的服务端 Action 绑定为交付内容：

```text
data/<namespace>/shop_products/<path>.json
```

```json
{
  "shop": "myaddon:orchard_stand",
  "item": "myaddon:orchard_blessing",
  "priority": 100,
  "action": {
    "type": "myaddon:heal",
    "data": {"health": 4.0}
  },
  "available_when": []
}
```

数据商品一次请求只允许购买一个单位，避免多个非事务 Action 部分成功后无法回滚。
`action` 成功才提交库存；Action 返回失败或抛异常时自动退款。需要批量语义、动态
选择或更复杂事务边界时，注册服务端 Java Handler：

```java
StardewShopProducts.register(id("orchard_blessing"), 100,
    context -> {
        if (!context.entry().item().equals(
                "myaddon:orchard_blessing")) {
            return StardewShopProductPreparation.pass();
        }
        return StardewShopProductPreparation.accept(
            grantContext -> {
                grantContext.player().heal(4.0F);
                return true;
            });
    });
```

Handler 按优先级从高到低、同优先级按注册 ID 排序。`pass()` 继续询问下一项；
`accept(grant)` 声明拥有该商品并捕获本次精确交付；`reject()` 声明拥有但当前
不可购买，并阻止较低优先级 Handler 接管。`prepare` 在扣款前运行，适合检查冷却、
是否已拥有和目标是否存在；被接受后，核心重新解析完整成本并支付，再调用准备好的
`grant`。它返回 `false` 或抛异常时，核心自动使用支付回执退款且不扣库存。
Handler 应在确认能够完成后再产生不可逆副作用；若它在返回 `false` 前已经修改附属
自己的状态，仍须自行恢复该状态。准备对象刻意把“选择交付”和“执行交付”分开，
避免支付改变玩家余额后重新解析到另一条规则。

默认情况下，`ACCEPT/REJECT` 会分别生成满足/阻断的
`SHOP_PRODUCT_ACCEPTED` Requirement。需要给冷却、目标不存在或附属进度提供具体
原因时，可使用四参数注册重载；解释 Provider 只能描述同一次权威决定，若报告与
`ACCEPT/REJECT` 相矛盾，核心会记录错误并退回通用说明：

```java
StardewShopProducts.register(MY_SERVICE_HANDLER, 100,
    context -> isMyService(context)
        ? (ready(context)
            ? StardewShopProductPreparation.accept(this::grantService)
            : StardewShopProductPreparation.reject())
        : StardewShopProductPreparation.pass(),
    (context, decision) -> new StardewRequirementReport(List.of(
        new StardewRequirement(
            id("orchard_service_ready"),
            decision == StardewShopProductDecision.ACCEPT
                ? StardewRequirement.State.SATISFIED
                : StardewRequirement.State.UNSATISFIED,
            Component.translatable(
                "requirement.myaddon.orchard_service_ready"),
            true
        )
    ))
);
```

`StardewShopProducts.requirements(context)` 可单独预检虚拟商品；
`StardewShopInventories.requirements` 已自动把选中 Handler 的报告与上架、条件和
库存报告合并。预检会运行 `prepare` 但不会扣款、扣库存或调用 `grant`，因此
`prepare` 本身仍必须无副作用。

本体的 `recipe:`、`wallpaper:` 和 `flooring:` 已迁移为低优先级内置 Handler，
不再由购买网络包硬编码。附属可用更高优先级有意覆盖它们，也可增加完全独立的商品
类型。虚拟商品成功响应不携带物品 ID，因此客户端不会生成光标物品或掉落物；实际
购买数量仍用于库存扣减。该流程同样适用于金币商店和展会星币商店。

有限库存默认保持旧语义：每位玩家独立、每天重置。无需修改稳定的
`StardewShopEntry` 构造器，可用独立数据规则改变某一行的库存所有者和周期：

```text
data/<namespace>/shop_stock_rules/<path>.json
```

```json
{
  "shop": "myaddon:orchard_stand",
  "item": "minecraft:apple",
  "priority": 100,
  "scope": "world",
  "reset": "season",
  "available_when": []
}
```

`scope` 为 `player` 或 `world`；`reset` 为 `day`、`week`、`season`、`year`
或 `never`。最高优先级的可用精确匹配规则生效，同优先级按规则资源 ID 排序。
购买账本存入世界 SavedData，重启不会恢复库存；跨日只清除已经结束的周期，不会
误清每周、每季、每年或永久限购。`stock` 仍是一个周期内的总数量，客户端看到的
只是服务端计算后的剩余量。若使用依赖玩家状态的 `available_when`，应避免让不同
玩家为同一商品解析出相互矛盾的 `player/world` 作用域。

交互绑定路径：

```text
data/<namespace>/shop_bindings/<path>.json
```

NPC 绑定只需 `shop` 和 `npc`。地点绑定使用 `dimension`、`min`、`max` 定义可右键的闭区间方盒；两种绑定都支持 `available_when`。
在非 `stardewcraft` 命名空间的绑定文件中，未带命名空间的 `shop` 和 `npc`
自动归入文件命名空间；引用本体或另一个附属时写完整 ID。旧本体绑定中的
`SeedShop`、`lewis` 等无命名空间 ID 继续原样解析。

{

  "background": 0,

## 剧情扩展

剧情仍放在：

```text
data/<namespace>/cutscene_events/<path>.json
```

第三方剧情 ID 必须与文件命名空间一致。只使用本体触发器和命令时，数据包无需 Java 代码即可新增剧情。
定义、地点/NPC/时间派生索引、原始同步 JSON、版本和内容哈希由一个目录快照发布。
登录与 reload 的网络 payload 会先捕获该快照再读取全部字段，避免跨 revision 拼包；
无效客户端同步同样保留上一版。

服务端触发器注册：

```java
StardewCutsceneTriggers.register(MY_TRIGGER_ID, Codec.INT,
    (player, minimumLevel) -> player.experienceLevel >= minimumLevel);
```

触发器 DTO 若保存确定的内容 ID，可使用四参数重载让依赖进入统一目录：

```java
StardewCutsceneTriggers.register(
    MY_NEARBY_NPC_TRIGGER_ID,
    NearbyNpcTrigger.CODEC,
    (player, data) -> isNear(player, data.npc()),
    (owner, data) -> List.of(
        StardewContentReference.required(
            StardewContentReferenceRoles.TARGET_NPC,
            new StardewContentKey(
                StardewContentTypes.NPC,
                data.npc()))));
```

剧情中的触发器写成：

```json
{"type": "myaddon:experience_level", "data": 10}
```

客户端演出命令必须只在 `Dist.CLIENT` 环境注册：

```java
StardewCutsceneCommands.register(MY_COMMAND_ID,
    data -> new MyVisualCommand(data));
```

需要强类型 payload 和引用诊断时，可以用 Codec 重载：

```java
StardewCutsceneCommands.register(
    MY_COMMAND_ID,
    MyVisualData.CODEC,
    MyVisualCommand::new,
    (owner, data) -> List.of(
        StardewContentReference.required(
            StardewContentReferenceRoles.DISPLAY_ITEM,
            new StardewContentKey(
                StardewContentTypes.ITEM,
                data.item()))));
```

命令 JSON 使用完整 ID 作为 `cmd`。旧的 JsonObject Factory 注册方式保持可用，也可用三参数重载为原始 JsonObject 注册引用 Provider；Provider 接收防御性副本。自定义演出命令只能负责画面、声音和客户端表现；修改金钱、物品、任务、Flag 等服务端状态必须使用 Action，不能藏在客户端命令里。

## 机器配方

机器配方位于：

```text
data/<namespace>/artisan/<path>.json
```

第三方推荐每个文件只定义一条配方，文件路径就是配方 ID：

```json
{
  "machine": "stardewcraft:keg",
  "input": "minecraft:apple",
  "output": "minecraft:golden_apple",
  "minutes": 60,
  "consume": 1,
  "outputCount": 1
}
```

`input` 与 `tag` 二选一；也可以使用 `inputMode: crop_type|mineral_type|fish_type`。分类模式通过公共物品元数据 API 判断，因此数据包标记或附属 Provider 提供分类的物品也能进入本体机器。机器和配方都使用命名空间 ID；旧本体的“一个文件内含 `recipes` 数组”格式继续兼容。

同一机器先匹配精确物品，再匹配标签，最后匹配分类模式；同级规则按完整配方 ID 排序。任何无效配方都会拒绝整次候选快照并保留上一版。

规范定义、按机器排序的运行时索引和客户端同步缓存属于同一个 revision。同步缓存仍可
在内存紧张时释放并从所属 Catalog 重建，但不会从另一个 reload revision 读取配方。
腌制原料元数据和它的同步 JSON 同样由一个目录实例持有；本体覆盖会在候选构建期完成后
再发布，客户端解析失败不会替换当前数据或遗留上一版缓存。

## 烹饪配方

现代烹饪配方路径：

```text
data/<namespace>/cooking/recipes/<path>.json
```

文件路径就是配方 ID，产物单独声明：

```json
{
  "output": "myaddon:apple_snack",
  "output_count": 1,
  "ingredients": [
    {"item": "minecraft:apple", "count": 2},
    {"tag": "c:milk", "count": 1, "display_item": "stardewcraft:milk"},
    {
      "categories": ["stardewcraft:fish", "stardewcraft:legendary_fish"],
      "count": 1,
      "display_item": "stardewcraft:sunfish"
    }
  ]
}
```

每种食材必须且只能使用 `item`、`tag`、`categories` 三种选择器之一。分类匹配通过公共物品元数据 API，因此附属物品不需要继承本体 Java 类。服务端负责重新验证配方、解锁状态、附近冰箱和玩家背包并执行扣料；客户端只负责显示和发起请求。

本体配方仍兼容原来的数字 token 表，但 reload 时会转换为同一套结构化定义。本体 `stardewcraft` 配方的存档 ID 继续使用旧路径，第三方配方在商店、解锁、存档、判重和制作时始终使用完整 `namespace:path`。无命名空间输入只作为本体旧数据兼容，不会默认解析为 `minecraft:*`。

烹饪定义、运行时查询和客户端同步 JSON 一次发布；解析或编码失败时，服务端制作、
客户端菜单和 JEI 继续消费上一份完整 revision。

服务端可重载路径：

```text
data/<namespace>/world_loot/*.json
data/<namespace>/forage_zones/*.json
data/<namespace>/mine_themes/*.json
data/<namespace>/mine_monster_spawns/*.json
data/<namespace>/locations/*.json
data/<namespace>/interior_portals/*.json
```

室内传送定义和解析后的运行时目标一次发布；无效候选不会留下新定义配旧坐标。
Java 动态目标与缺失目标时的世界锚点回退仍是独立兼容层，不会被数据包 reload 清空。
世界战利品、采集区、矿层主题和矿井刷怪表也各自把规范定义与确定性优先级表绑定为
一个 revision。它们仍是独立领域目录；一次 reload 中某个无效目录不会回滚无关目录。

### 逻辑地点

`data/<namespace>/locations/<path>.json` 定义的边界可通过
`StardewLocations` 作为统一逻辑地点查询。运行时 DTO 保留完整地点 ID、维度、
边界、别名、ledger ID、优先级、父地点、展示信息和解析后的环境；查询同时比较
维度和坐标，不会把其他维度中相同坐标误判为该地点。

```json
{
  "dimension": "stardewcraft:stardew_valley",
  "min": [-170, 55, 65],
  "max": [-120, 90, 115],
  "aliases": ["example_orchard"],
  "priority": 50,
  "indoor": false,
  "parent": "stardewcraft:forest",
  "display_name": {"translate": "location.myaddon.orchard"},
  "description": {"translate": "location.myaddon.orchard.description"},
  "icon": "myaddon:textures/gui/location/orchard.png",
  "tags": ["myaddon:orchard", "stardewcraft:forage"],
  "properties": {
    "stardewcraft:climate": "temperate",
    "stardewcraft:music_profile": "myaddon:music.orchard",
    "stardewcraft:music_start_time": "0600",
    "stardewcraft:music_end_time": "1800",
    "myaddon:primary_fruit": "apple"
  }
}
```

```java
StardewLocations.find(level, position).ifPresent(location -> {
    ResourceLocation locationId = location.id();
    boolean isForestOrChild = StardewLocations.isWithin(
        locationId,
        ResourceLocation.fromNamespaceAndPath(
            "stardewcraft", "forest")
    );
    List<StardewLocation> path =
        StardewLocations.hierarchy(locationId);
    Optional<String> climate = location.property(
        StardewLocationEnvironmentKeys.CLIMATE
    );
});
```

`indoor` 默认为 `false`，所以旧附属地点不会因加入统一目录而被误当作固定室内；
真正的室内地点应显式写 `"indoor": true`。现有 `InteriorRegionRegistry` 方法只
投影这些室内地点并继续兼容。父引用必须存在且不能形成环，alias 冲突也会使整批
reload 回滚。子地点继承父地点的 `tags` 和 `properties`，同名属性由子地点覆盖；
`indoor/outdoor` 标签按子地点自己的最终环境重新投影。标签和属性 ID 必须带
命名空间，第三方属性应使用自己的命名空间。

`stardewcraft:music_profile` 是已注册 `SoundEvent` 的完整 ID。客户端在最终
逻辑地点内、`music_start_time`（包含）到 `music_end_time`（不包含）的窗口中
播放它；时间属性使用 `0000` 至 `2600` 的 HHMM 字符串，并支持跨午夜窗口。
不写时间时全天生效；写 `stardewcraft:silent` 会在窗口内明确静音。未知声音、
非法时间，或整个父链都没有 profile 的孤立时间字段会使整批地点 reload 回滚，
而不是把坏定义同步给客户端。子地点可以单独覆盖父地点的曲目或时间属性；窗口外
继续走现有天气、季节和
旧固定室内音乐回退，因此旧地图与旧附属无需迁移。
机器可读约束见 `docs/schemas/location-v1.schema.json`；运行时 Codec 与 reload
还会继续验证父地点、alias 冲突、声音注册项和继承关系。

钓鱼地点解析会按“最具体地点 → 所有父地点”加入完整 ID 和别名，JEI 对已知逻辑
地点直接使用同步后的 `display_name`；节日声明父地点时，玩家位于任意子地点也会
通过权威地点验证。遗物点上下文仍提供最具体的只读地点 DTO，附属可用
`StardewLocations.hierarchy(...)` 查看完整语义路径。这样地图附属定义一次地点后，
可以被展示、钓鱼、掉落、NPC、任务和节日系统共同消费，而不必重复坐标或字符串表。

本体已有 Town、Beach、Forest、Mountain、Desert、Backwoods、BusStop、Railroad
和 Woods 范围也已投影到同一目录；坐标直接复用现有采集区数据，Mountain 保留两个
不连续的精确区域。旧大小写地点名继续作为 alias，新的跨系统引用应使用
`stardewcraft:town` 等完整 ID。

`world_loot` 用 `source + group` 接入现有算法。内置 source 为 `stardewcraft:artifact_spot`、`stardewcraft:quarry` 和 `stardewcraft:skull_cavern_treasure`；条目使用公共 Item Query，并支持 `weighted` 或 `sequential` 模式。蚯蚓点的 `group` 是运行时地点组的小写名称。

`forage_zones` 声明一个或多个 AABB、季节方块、每日数量和地表类型。它只在已有世界区域生成已注册方块。`mine_themes` 声明楼层范围、优先级、石材/装饰/矿石池，并绑定本体已有的 `mechanic_id`；地形算法仍在 Java。

附属自定义怪物应先注册完整 Profile，令实体身份、配置和击杀进度语义彼此绑定：

```java
StardewMineMonsterProfiles.register(
    MY_CLOCKWORK_PROFILE,
    MyEntities.CLOCKWORK_MONSTER.get(),
    Set.of("myaddon:clockwork"),
    (mob, context) -> configureClockworkMonster(
        mob, context.floor())
);
```

通常的楼层分布放在数据包，而不是写死在 Java：

```text
data/myaddon/mine_monster_spawns/clockwork_floor.json
```

```json
{
  "min_floor": 13,
  "max_floor": 30,
  "priority": 100,
  "mechanics": ["earth"],
  "dark": false,
  "min_distance": 6.0,
  "max_distance": 40.0,
  "entries": [
    {"profile": "myaddon:clockwork", "weight": 3},
    {"profile": "stardewcraft:green_slime", "weight": 1}
  ]
}
```

`themes` 可精确引用 `mine_themes` 文件 ID，`mechanics` 可匹配主题的
`mechanic_id`；两者同时出现时必须有交集。省略它们表示所有主题，省略 `dark`
表示明暗都匹配。距离包含边界。表按 `priority` 从高到低、同优先级按完整文件 ID
排序，第一张匹配表按正整数 `weight` 选择 Profile。

未知主题、mechanic 或 Profile、空条目、反向范围和权重溢出都会拒绝整批刷怪表
reload，并保留上一份快照。没有表匹配时不会改变本体概率。

只有依赖玩家状态、世界事件或其它动态算法时才注册 Java 选择器：

```java
StardewMineMonsterProfiles.registerSelector(
    MY_CLOCKWORK_SELECTOR,
    100,
    context -> context.floor() == 13
        ? MY_CLOCKWORK_PROFILE
        : null
);
```

最终顺序是“动态 Profile 选择器 → 数据包刷怪表 → 旧 EntityType Provider →
本体瀑布概率”。选择器返回 Profile ID，而不是只返回实体类型。核心会在实体进入矿井事件之前携带
Profile 身份，随后验证实体类型、加入进度标签并执行权威配置器；单个选择器或配置器
异常只拒绝该候选/生成。`progressTags` 同时连接公会讨伐目标与日常委托中的
`monster_tags/type`，所以附属不需要再修改本体击杀分派。Profile 以
`stardewcraft:mine_monster_profile` 进入统一内容图并引用实际实体类型，缺少对应
Profile 的公会或日常怪物标签会成为节点 issue。

刷怪表以 `stardewcraft:mine_monster_spawn_table` 进入同一内容图，必需引用精确
主题和所有候选 Profile；按 mechanic 匹配的表会连接当前所有对应主题。因此地图、
矿层主题、怪物实现与任务进度可以分别由不同附属提供，同时在 reload 后统一诊断。

旧 `StardewMineMonsterProviders.register(...)` 继续兼容，适合选择本体已经认识并
会配置的原版映射实体（如 `EntityType.SILVERFISH`）。它只携带 `EntityType`，无法
描述附属实体的属性和进度语义，因此新的自定义怪物应使用 Profile 入口。

`locations` 是供展示、音乐、任务、NPC、节日与室内识别共享的分层地点元数据；
客户端需要的完整定义会在登录和 reload 后同步。`interior_portals` 只注册目的地，
触发方块、权限和结构放置仍由世界逻辑负责。固定预生成室内继续保留原坐标迁移
边界，不能靠数据包平移。

### 有界世界事件（实验）

临时修改世界的活动使用 `StardewWorldEvents`，不应直接在多个 tick 回调中逐块放置。
调用者先通过地点、区域或锚点解析服务端坐标，再提交唯一实例 UUID：

```java
StardewWorldEvents.register(MY_BLOSSOM_EVENT, context -> {
    BlockPos target = context.origin();
    CompoundTag state = new CompoundTag();
    state.putString("season", "spring");
    return new StardewWorldEvents.Plan(
        List.of(new StardewWorldEvents.BlockChange(
            target,
            context.level().getBlockState(target),
            Blocks.PINK_WOOL.defaultBlockState()
        )),
        state
    );
});

StardewWorldEvents.Result result = StardewWorldEvents.start(
    new StardewWorldEvents.Context(
        MY_BLOSSOM_EVENT,
        instanceId,
        level,
        resolvedAnchor,
        seed,
        new CompoundTag()
    )
);
```

本体会在写世界前验证整份计划：最多 1024 个不重复位置、区块已加载、方块仍等于
`expected`、没有无效或无变化条目，并拒绝涉及方块实体的计划。全部预检通过后才按序
写入；中途失败会反向回滚，回滚也失败时会持久化 recovery ledger，供稍后再次清理。

同一活动实例 UUID 重复启动返回 `ALREADY_ACTIVE`，不会再次调用处理器。清理时整份
计划必须仍保持替换状态，否则返回 `CONFLICT` 且一个方块也不恢复。成功提交后，本体
保存完整事件类型、维度、原点、owner payload 和每个方块的精确逆操作，因此定义该
事件的附属暂时缺失时仍可调用：

```java
StardewWorldEvents.cleanup(server, instanceId);
```

owner payload 的 NBT 编码上限为 64 KiB，只能用精确事件类型读取。该实验入口刻意不接受
实体、容器 NBT、任意脚本或未加载区块；需要这些能力的事件应先拆成可补偿的领域操作，
不能绕过本体事务直接宣称原子性。

## 农业与装备

同步 Data Map 路径：

```text
data/stardewcraft/data_maps/block/stardew_crop_data.json
data/stardewcraft/data_maps/block/stardew_tree_data.json
data/stardewcraft/data_maps/block/stardew_building_data.json
data/stardewcraft/data_maps/entity_type/stardew_animal_data.json
data/stardewcraft/data_maps/item/stardew_equipment_data.json
```

静态对象用 Data Map；依赖方块位置、实体状态、NBT 或附魔的内容用 `StardewAgricultureDataApi` 和 `StardewEquipmentDataApi` 的有序 Provider。Provider 优先于 Data Map，同优先级按完整 ID 排序，重复 ID 直接报错。

农业 Provider 从不可变快照中读取，不在调用附属代码时持有注册锁。单个 Provider 抛出运行时异常会记录 Provider ID 和目标 ID，然后继续下一个 Provider，最后回退 Data Map。

当前本体运行时消费边界如下：

| 数据 | 会影响的本体流程 | 仅元数据字段 |
| --- | --- | --- |
| Crop | `StardewCropBlock` 收获时使用带 `level + pos` 的 Provider 解析 `farming_experience`；附属作物可通过下述 runtime adapter 接入换日 | 其他字段不会自动改写任意方块的存档或交互 |
| Tree | 本体果树根方块使用 `product` / `product_count` / `max_stored_product` / `fruit_seasons` | `kind` / `days_to_mature` |
| Animal Data Map | 没有完整动物定义的旧附属仍可使用 `produce` / `produce_interval_days` 回退 | `building_type` / `purchase_price` / `days_to_mature` |
| Building | 鸡舍、畜棚管理方块建造时使用 `capacity`，购买/孵化时检查非空 `accepted_animals` | `type` / `required_interior_blocks` |

这些 Data Map 不会单独把任意 Minecraft 方块或实体改造成 StardewCraft 作物、果树、
农场动物或建筑。例如任意方块没有通用的果实存储 Block Entity，已经建成的自由形状
建筑也没有安全的“必需方块自动放置”语义。元数据字段可供附属查询；需要运行时行为
时使用对应适配器或能力入口。

### 非继承型作物运行时

代码附属可注册自己的作物类型，而不继承 `StardewCropBlock`：

```java
StardewCropTypes.register(
    new StardewCropType(
        id("moonberry"),
        "block.myaddon.moonberry_crop",
        5,
        List.of(id("moonberry_crop")),
        new StardewCropData(
            List.of("fall"), List.of(1, 2, 2, 3), 4, 12,
            id("grab"), id("moonberry"), id("moonberry_seeds")
        )
    ),
    100,
    new StardewCropRuntimeAdapter() {
        @Override
        public StardewCropState inspect(LevelReader level, BlockPos pos) {
            if (!level.getBlockState(pos).is(MyBlocks.MOONBERRY_CROP)) {
                return null;
            }
            // stage/mature 应从附属自己的 BlockState 或 BlockEntity 读取。
            return new StardewCropState(
                id("moonberry"), pos, StardewCropState.Part.ROOT,
                readStage(level, pos), isMature(level, pos),
                List.of(pos.below())
            );
        }

        @Override
        public DailyResult growOneDay(
                ServerLevel level,
                StardewCropState crop,
                StardewCropDailyContext context) {
            // context 提供浇水、季节、地点季节豁免、绝对日期和离线补算标记。
            return advanceAddonState(level, crop.root(), context);
        }

        @Override
        public StardewCropHarvestResult harvest(
                ServerLevel level,
                StardewCropState crop,
                StardewCropHarvestContext context,
                Consumer<ItemStack> output) {
            if (!crop.mature()) {
                return StardewCropHarvestResult.notReady();
            }
            if (requiresScythe() &&
                    context.source() == StardewCropHarvestContext.Source.PLAYER) {
                return StardewCropHarvestResult.wrongTool();
            }
            // 先提交附属自己的移除/再生状态，再把所有主产物和副产物写入暂存 sink。
            commitRegrowth(level, crop.root());
            output.accept(new ItemStack(MyItems.MOONBERRY.get(), 2));
            return StardewCropHarvestResult.harvested(12);
        }
    }
);
```

放置根方块后调用 `StardewCropRuntime.track(level, root, planterUuid)`，移除时调用
`untrack`。位置进入本体已有的持久化换日索引；每日生长、立即过季检查、离线补算
和耕地保护都会识别该适配器。重复登记位置是安全的，世界存档仍沿用原 `Crops`
列表，不迁移已有数据。调度器只保存位置与可选种植者；阶段、再生、变种和死亡状态
由附属自己持久化。

`StardewCropState.soilPositions` 明确列出该逻辑作物依赖的耕地点，顺序应稳定且第一项
作为主土壤。本体单格作物自动投影为 `root.below()`；多格温室架或异形作物可返回多个
位置。换日浇水判断、喷壶命中、质量肥料发芽限制和农场电脑未浇水统计都会消费这份
几何，而不再猜测附属方块必须恰好位于一格耕地上方。

`StardewCropType.blockIds` 必须列出适配器可能识别的全部根/上层/扩展方块 ID。
注册表据此建立按方块 ID 的不可变索引；喷壶、Jade 等高频查询先做 O(1) 预筛选，
不会在玩家看向任意石头时遍历所有附属适配器。`data` 可复用同一个
`StardewCropData` 声明季节、阶段、再生、经验、收获方式、产物和种子；位置相关差异
仍可由已有 `StardewAgricultureDataApi` Provider 覆盖。

`inspect` 必须只读且可在客户端调用。运行时按 priority 降序、完整注册 ID 升序检查，
本体作物优先；异常适配器会被隔离。变更前后都会重新确认类型 ID、根位置和
`visualStageCount` 边界，方块已被替换时会自动从调度器清理。管理员可用
`/stardew debug world here` 查看类型、逻辑根、部件、阶段、成熟度、土壤列表和是否
已登记换日。

收获通过 `StardewCropHarvestContext` 区分 `PLAYER`、`TOOL` 和 `AUTOMATION`，
并携带只读工具副本、农业等级与强制工具标志。适配器把物品写入暂存 sink；只有返回
`HARVESTED` 后本体才会复制并投递这些物品，所以 `NOT_READY`、`WRONG_TOOL`、
`PASS` 或异常不会泄漏暂存产物。玩家路径在服务器检查农场权限、于作物根位置生成
掉落并统一授予返回的农业经验；自动化路径把所有产物交给调用者且永不授予经验。
适配器仍拥有任意几何作物的移除/再生提交，因为本体不能安全猜测附属的 BlockState
或 BlockEntity 布局。

附属方块的普通右键可调用
`StardewCropRuntime.harvestForPlayer(player, pos, hand, false, false)`；镰刀范围收割、
Junimo 小屋和 Create 假玩家收割已经直接消费同一协议。其他自动化应调用
`harvestForAutomation(level, pos, farmingLevel, output)`，不要创建伪玩家来绕过事务。

乌鸦与农场杂物扩散不是收获，不能复用产物/再生逻辑。适配器应按需实现
`remove(level, crop, cause)`，清理完整多格结构并且不产生物品；返回成功后本体才删除
换日索引。当前标准 cause 为 `CROW`、`FARM_DEBRIS`、`ADMIN` 和 `OTHER`。未实现删除
的附属作物会安全保留，而不是由本体猜测其结构并只删掉根方块。

Jade 的服务端数据 Provider 通过 block-ID 索引覆盖附属方块，并同步类型翻译键、
阶段、最大阶段、成熟度、浇水状态和镰刀提示；核心作物继续保留精确 phase-day 与
再生倒计时显示。作物描述中的 `produce` 还会自动投影为
`StardewAcquisitionSource.Kind.FARMING`，所以图鉴/获得来源查询能说明该物品由哪种
作物收获，不需要每个附属再注册一遍 acquisition Provider。

新附属动物的静态玩法定义应优先放入模组 JAR 的内置数据包：

```text
data/myaddon/stardewcraft/farm_animals/goose.json
```

该文件统一声明住宅、成熟、生产周期、普通/豪华产物、工具、职业、商店、售价、
实体类型、声音和翻译键；它与本体动物和用户数据包走同一个可 `/reload` 的事务化
快照。完整 schema、覆盖规则与最小示例见 `ANIMAL_DATA_PACK.md`。如果
`entity_type` 指向附属自己的实体，该实体必须继承 `BaseCoopAnimalEntity` 并按普通
NeoForge 流程注册；如果只做纯数据变体，也可以复用一个已有 managed animal 实体。

动物建筑等级的容量、怀孕能力、自动喂食、原版费用、材料和施工天数使用另一组
服务端资源：

```text
data/myaddon/stardewcraft/animal_buildings/*.json
```

该资源可用唯一的 `"replace": true` 覆盖既有 `family:tier`，并与动物定义一起在
`/reload` 时先验证完整候选快照再原子发布。它不负责自由建筑的 3D 结构识别；新增
全新建筑 family 仍需要代码模组提供管理器与结构验证。完整字段和示例同样见
`ANIMAL_DATA_PACK.md`。

下列 Java 注册入口保留给旧附属兼容。没有完整 JSON 时，附属注册的实体若继承
`BaseCoopAnimalEntity`，仍可进入托管动物记录到世界实体的投影流程：

```java
StardewAnimalTypes.register(
    ResourceLocation.fromNamespaceAndPath("myaddon", "goose"),
    "myaddon:goose",
    "coop",
    5,
    MyEntities.GOOSE::get
);
```

第一个 ID 标识注册来源，重复时立即报错；第二个字符串是写入动物存档的类型 ID。新附属应使用带命名空间的类型 ID，迁移已有附属时也可以继续注册原来的无命名空间 ID，避免破坏旧世界。实体类型使用延迟 `Supplier`，因此可以在附属构造阶段、NeoForge 实体注册事件完成前登记。

该旧入口负责 `AnimalTypeCatalog` 元数据、已知类型枚举和
`AnimalEntitySyncService` 实体解析，可以替代附属对这两个内部类的注入。完整 JSON
定义存在时，数据中的 `entity_type`、`family`、`days_to_mature` 和生产字段优先；
旧 Java 注册只作为缺失定义时的实体投影、购买入口和旧存档兼容层。没有完整动物
JSON 时，本体不会用白鸡参数猜测生产、照料、吃草、饼干或繁殖；核心日结保持暂停，
附属若必须继续维护这种旧记录，应注册 `StardewAnimalDailyHandlers` 并完整承担状态
迁移。推荐补齐同 ID 的 JSON，让本体 reducer 恢复源码一致的完整日结。

旧附属需要在玛妮商店出售时，可以继续登记独立的服务端购买条目：

```java
StardewAnimalShopEntries.register(new StardewAnimalShopEntry(
    ResourceLocation.fromNamespaceAndPath("myaddon", "goose_shop"),
    "myaddon:goose",
    "coop",
    2,
    12000,
    "Goose",
    "entity.myaddon.goose",
    "myaddon.animal.shop.desc.goose",
    "myaddon.animal.shop.lock.coop_t2",
    100
));
```

旧商店条目只有在同类型的 `StardewAnimalTypes` 注册存在、且 `family` 一致时才会
进入购买链。完整 JSON 定义则用 `purchase_price >= 0` 自动进入商店，并使用
`required_building_tier`、`shop_order` 和可选 `unlock_condition`。客户端提交的价格、
建筑权限、建筑等级、容量、解锁条件和最终实体类型都会由服务端重新读取，不能靠
伪造客户端卡片购买未注册动物。

自定义孵化物品通过有序 resolver 接入，静态配方仍放在 `artisan` 数据中：

```java
StardewAnimalIncubation.register(
    ResourceLocation.fromNamespaceAndPath("myaddon", "goose_egg"),
    100,
    stack -> stack.is(MyItems.GOOSE_EGG.get()) ? "myaddon:goose" : null
);
```

Resolver 只在本体孵化蛋均不匹配后执行。优先级从高到低，同优先级按完整注册 ID 排序；返回 `null` 继续后续 resolver。异常会记录具体注册 ID 并继续，未注册的动物类型会被拒绝，避免消耗物品后生成无法投影实体的孤立记录。

孵化器会根据 resolver 返回类型在 `StardewAnimalTypes` 中登记的 `family` 选择包含当前位置的建筑，不再把附属蛋固定解释为鸡舍动物。自动孵化和手动领取会再次验证同一建筑族、容量、操作权限、名称和实体映射。旧 `getContainingAnimalBuilding` 与 `resolveAnimalTypeId` 方法保留，因此未迁移附属的注入仍可命中。

复杂的成长和产物逻辑通过按动物类型注册的日结 Handler 接入：

```java
StardewAnimalDailyHandlers.register(
    ResourceLocation.fromNamespaceAndPath("myaddon", "goose_daily"),
    "myaddon:goose",
    100,
    context -> {
        if (context.isBaby() || context.daysSinceLastProduce() < 2) {
            return StardewAnimalDailyHandlers.Result.SKIP_DEFAULT_PRODUCTION;
        }

        ItemStack egg = new ItemStack(MyItems.GOOSE_EGG.get());
        if (context.placeOvernightProduce(egg, true)) {
            context.resetProduceCooldown();
        }
        return StardewAnimalDailyHandlers.Result.SKIP_DEFAULT_PRODUCTION;
    }
);
```

对有完整 JSON 的动物，Handler 在服务端动物日结时、产出冷却与回舍处理后运行。
`PASS` 会继续下一个 Handler 和本体默认产出；`SKIP_DEFAULT_PRODUCTION` 表示该动物
当天的默认产出已经由附属接管，但不会跳过本体的喂食、心情、抚摸、成长、离线追赶
或存档处理。对只有旧 Java 类型元数据、没有完整 JSON 的动物，Handler 是唯一会执行
的日结逻辑，本体不会先应用任何猜测参数。多个 Handler 按优先级从高到低、同优先级
按完整注册 ID 排序；单个 Handler 异常会记录来源并继续后续 Handler。

`StardewAnimalDailyContext` 是受控状态门面，提供动物 ID、类型、年龄、成熟天数、好感、心情、饱食度、产出冷却和 Animal Cracker 状态。它还提供增长/照料调整、冷却重置、手持产物保存以及建筑内放置或掉落产物的操作。离线追赶时 `placeOvernightProduce` 始终返回 `false`，避免为未加载的历史天数补放世界实体。

不参与随机怀孕的动物可以登记繁殖否决规则：

```java
StardewAnimalReproductionRules.register(
    ResourceLocation.fromNamespaceAndPath("myaddon", "camel_reproduction"),
    "myaddon:camel",
    100,
    context -> StardewAnimalReproductionRules.Decision.DENY
);
```

繁殖规则只在本体已经确认动物成年、玩家开启繁殖、建筑有容量后参与候选筛选。它只能返回 `PASS` 或 `DENY`，不能绕过玩家开关、建筑类型和容量校验。规则同样使用稳定优先级和异常隔离，异常按 `PASS` 处理。

猪挖出松露后的稀有替换通过独立的有序事件接入：

```java
StardewTruffleFoundHandlers.register(
    ResourceLocation.fromNamespaceAndPath("myaddon", "golden_truffle"),
    100,
    context -> {
        if (!context.animalTypeId().equals("myaddon:golden_pig")) {
            return StardewTruffleFoundHandlers.Result.PASS;
        }
        // 在 context.anchor() 附近成功创建附属自己的实体或物品。
        return StardewTruffleFoundHandlers.Result.REPLACE_TRUFFLE;
    }
);
```

`PASS` 会继续后续 Handler；全部通过后，本体才执行源码的 0.2% Truffle Crab
替换和普通松露落地。只有已经成功创建替代内容时才能返回 `REPLACE_TRUFFLE`；
异常会隔离并继续，不会吞掉松露。Context 中的 `ItemStack` 是防御性副本，修改它
不会修改权威产物。处理器按优先级从高到低、同优先级按完整注册 ID 排序。

这些入口插入 `AnimalGrowthManager` 的日结、繁殖和松露流程，但保留原方法、调用
顺序和默认分支。因此尚未迁移的附属仍可继续使用现有 mixin；迁移后的新动物可以
用日结 Handler 替代“每日注入 + 屏蔽默认产出”，特殊繁殖可用规则替代对应
redirect，松露替换不需要注入猪实体。

动物查询页的出售规则和繁殖开关能力由服务端定义，购买页图标则使用不含行为的客户端安全描述：

```java
StardewAnimalQueryDefinitions.register(new StardewAnimalQueryDefinition(
    ResourceLocation.fromNamespaceAndPath("myaddon", "camel_query"),
    "myaddon:camel",
    28616,
    37200,
    false
));

StardewAnimalPurchaseDisplays.register(new StardewAnimalPurchaseDisplay(
    ResourceLocation.fromNamespaceAndPath("myaddon", "camel_purchase_icon"),
    "myaddon:camel",
    ResourceLocation.fromNamespaceAndPath(
        "myaddon", "textures/gui/animal_query/icon_camel.png"),
    32,
    16
));
```

出售价格沿用本体公式 `min(maximumSellPrice, floor(sellBasePrice * (friendship / 1000 + 0.3)))`。查询菜单只同步计算结果和开关能力，出售和切换操作仍按当前权威动物记录、成年状态和建筑权限在服务端重验。购买图标不进入服务端购买判定；缺少图标只会让该条目不绘制，不会改变价格、解锁或建筑限制。

鸡舍和畜棚管理页的动物数量现在取“建筑成员 ID 与权威动物记录计数的较大值”，因此旧存档或附属迁移期间成员集合尚未补齐时也不会错误允许拆除。该修正属于本体只读投影，不开放可伪造数量的 Provider。

附属需要给单只托管动物保存遗传、特殊冷却或剧情状态时，应注册版本化 Key，而不是向本体固定字段或实体临时 NBT 注入：

```java
StardewAnimalPersistentData.Key GOOSE_STATE =
    StardewAnimalPersistentData.register(
        ResourceLocation.fromNamespaceAndPath("myaddon", "goose_state"),
        2
    );

StardewAnimalDailyHandlers.register(
    ResourceLocation.fromNamespaceAndPath("myaddon", "goose_state_update"),
    "myaddon:goose",
    50,
    context -> {
        StardewAnimalPersistentData.Value stored =
            context.persistentData(GOOSE_STATE).orElse(null);
        CompoundTag data = stored == null ? new CompoundTag() : stored.payload();

        if (stored != null && stored.storedVersion() < GOOSE_STATE.currentVersion()) {
            // 在这里按附属自己的规则迁移旧字段。
        }
        data.putInt("days_observed", data.getInt("days_observed") + 1);
        context.setPersistentData(GOOSE_STATE, data);
        return StardewAnimalDailyHandlers.Result.PASS;
    }
);
```

注册 ID 必须唯一，返回的 `Key` 是本次运行时的写权限 token，不能自行构造。写入总是使用 Key 的当前版本，并通过权威 `AnimalWorldData` 自动标记存档已修改；日结之外可以使用 `StardewAnimalPersistentData.read/write/remove(ServerLevel, animalId, key, ...)`。读取返回防御性 NBT 副本，一个附属修改副本不会影响记录或其他命名空间。

存档使用每个 `ResourceLocation` 独立的 `{version, payload}` 条目。未安装附属、尚未注册的 ID，以及本体不理解的合法数据都会在读档和再次保存时原样保留；旧世界没有该容器时不会补写空标签。版本迁移由拥有 Key 的附属显式执行，本体不会猜测或降级第三方 schema。

自定义动物实体若需要在自己的 GeckoLib Controller 中读取本体进食状态，可以直接调用继承到的 `isPlayingEatAnimation()`；不再需要访问 `eatAnimationTicks` 私有字段。本体仍保留该字段，供尚未迁移的 accessor mixin 使用。

## 可注册农场布局

`StardewFarmLayout` 和 `StardewFarmLayouts` 是实验接口，用来替代业务流程对
`FarmType` 固定枚举的依赖。附属在 Mod 构造阶段注册完整的命名空间描述：

```java
ResourceLocation layoutId =
    ResourceLocation.fromNamespaceAndPath("myaddon", "orchard");

StardewFarmLayout orchardLayout = new StardewFarmLayout(
    layoutId,
    true,
    Component.translatable("farm.myaddon.orchard"),
    Component.translatable("farm.myaddon.orchard.description"),
    ResourceLocation.fromNamespaceAndPath(
        "myaddon", "textures/gui/farm/orchard.png"),
    ResourceLocation.fromNamespaceAndPath(
        "myaddon", "farm/orchard.schem"),
    0,
    320, 32, 360,
    SPAWN, 90.0F,
    GREENHOUSE, TOTEM,
    SOUTH_ENTRY, EAST_ENTRY, WEST_ENTRY,
    "minecraft:plains",
    FORAGE_MIN, FORAGE_MAX,
    CAVE_BLACK_WALL, CAVE_PORTAL_WALL, CAVE_CLEAR_BOX,
    CAVE_EXIT, -90.0F
);

ResourceLocation cabins =
    ResourceLocation.fromNamespaceAndPath("myaddon", "starter_cabins");
ResourceLocation waterStyle =
    ResourceLocation.fromNamespaceAndPath("myaddon", "water_style");

StardewFarmLayouts.register(
    orchardLayout,
    3,
    List.of(
        StardewFarmLayoutConfigField.integer(
            cabins,
            Component.translatable("farm.myaddon.option.starter_cabins"),
            Component.translatable("farm.myaddon.option.starter_cabins.description"),
            1, 0, 4
        ),
        StardewFarmLayoutConfigField.choice(
            waterStyle,
            Component.translatable("farm.myaddon.option.water_style"),
            Component.empty(),
            "ponds",
            List.of("ponds", "river", "dry")
        )
    ),
    List.of(
        new StardewFarmLayoutAttachment(
            ResourceLocation.fromNamespaceAndPath(
                "myaddon", "orchard_festival_stage"),
            new BlockPos(144, 4, 92),
            180.0F,
            Set.of(StardewFarmLayoutAttachmentKeys.FESTIVAL)
        )
    )

```

结构资源 ID `myaddon:farm/orchard.schem` 对应附属 JAR 中的
`data/myaddon/structures/farm/orchard.schem`；图标仍是普通资源包纹理。每个布局
必须完整声明尺寸、出生点、温室/图腾位置、三个公共入口、可选采集区和洞穴区域。
宽和长不得超过单个 `512×512` 农场槽位。`selectable=false` 的布局可保留旧存档
解析或作为将来内容，但不会允许新建。

不需要 Java 行为的布局可以直接放在

完整字段约束见
[`docs/schemas/farm-layout-v1.schema.json`](schemas/farm-layout-v1.schema.json)；
可安装的非选择型示例见
[`orchard_preview.json`](../examples/stardewcraft-addon/src/main/resources/data/example_stardew_addon/farm_layouts/orchard_preview.json)。
没有命名空间的 `schematic`、配置字段和挂点 ID 自动使用定义文件的命名空间。
洞穴的 `black_wall`、`portal_wall`、`clear_box` 和 `exit` 可以独立省略。

农场布局 reload 是整批事务：所有 JSON、类型化默认值、Java/数据 ID 冲突和
`data/<namespace>/structures/...` 结构引用都验证成功后，才一次性替换当前数据
目录；任意定义失败会保留上一次完整快照。Java 注册与数据定义不能占用同一 ID，
避免加载顺序暗中决定胜者。管理员用 `/stardew debug farm-layouts` 可查看当前
数据 revision、活动数量、最近一次 reload 是否被拒绝和逐条原因。

提高纯数据定义的 `version` 只影响之后创建的农场。已有农场继续使用创建时保存的
几何和配置快照；需要修改已放置方块或主动采用新几何时，仍应由 Java 附属注册下面
的显式迁移。这样移除或错误更新数据包不会静默破坏旧世界。

旧的 `register(layout)` 仍等价于“版本 1、无配置字段”。配置字段只允许
`BOOLEAN`、有上下界的 `INTEGER` 和有限 `CHOICE`；选择页由服务端发送独立的
`StardewFarmLayoutPreview`，其中只有 ID、文字、图标、版本和配置 schema，不会
把 schematic、坐标、洞穴边界或 Handler 暴露给客户端。提交后服务端会再次拒绝
未知字段、非法值和不可选布局，再应用默认值并把规范化配置写入农场存档。
生命周期与初始化回调可通过
`context.farm().farmLayoutConfiguration()` 和
`context.farm().farmLayoutVersion()` 读取同一份不可变快照。

第四个注册参数是命名的农场相对挂点。NPC、节日、Portal 和附属建筑用完整 ID
引用挂点，不应再按布局 ID 维护第二份坐标表；回调中使用
`context.farm().resolveLayoutAttachment(id)` 得到当前农场实例的世界坐标。
非回调代码可用 `StardewFarms.find(server, ownerUuid)`、
`findForPlayer(server, playerUuid)` 或 `all(server)` 取得相同只读快照；
`tags` 用于发现 `NPC`、`FESTIVAL`、`BUILDING`、`PORTAL` 等能力，同 ID 的显式
挂点会覆盖由旧字段投影出的默认点。本体会为所有旧布局自动投影 `SPAWN`、
`GREENHOUSE`、`FARM_TOTEM`、三个入口和可选洞穴出口，因此旧注册代码无需修改。
挂点与几何一样写入农场快照，附属暂时缺失、所有权转移后仍会保留。

选择 payload 发送完整布局 ID，服务端重新查找并验证 `selectable` 后才创建农场。
创建时会把布局几何快照写入农场存档；因此附属暂时移除或之后修改注册值时，已经
存在的农场仍保持原边界、入口、出生点和洞穴位置。附属重新安装后，新农场使用新的
注册描述。布局快照不替代结构资源：从未完成初始化的农场仍需要原附属结构文件才能
实际放置地形。

旧 `FarmType` 枚举、旧构造函数和 `FarmType` 存档字段继续保留。旧世界第一次读写
时会映射到 `stardewcraft:<type>`，不要求一次性迁移；附属布局通过旧
`getFarmType()` 观察时会降级为 `STANDARD`，新代码必须使用
`getFarmLayoutId()` 或不可变农场快照中的完整 ID。

提高布局注册版本不会自动覆盖旧农场的几何快照。需要修改已经放置的世界内容时，
按目标版本注册显式、可重试的迁移：

```java
StardewFarmLayoutMigrations.register(
    layoutId,
    3,
    StardewFarmLayoutMigrations.FailurePolicy.STOP,
    StardewFarmLayoutMigrations.SnapshotPolicy.PRESERVE,
    context -> {
        int cabinCount = context.configuration()
            .integerValue(cabins, 1);
        // 只修改本版本负责的方块/实体；重复执行前先检查目标状态。
    }
);
```

迁移按目标版本升序运行，只有成功后才更新存档版本；异常会记录布局、目标版本和
农场主人，失败版本会在下次初始化或登录时重试。附属暂时缺失时，本体保留布局 ID、
旧版本、配置和几何快照，不猜测升级，也不删除未知配置。新建农场直接从当前注册版本
开始，不会执行历史迁移。管理员可用 `/stardew debug farm-layouts` 查看当前版本、
尺寸、可选择状态和配置字段。

默认 `PRESERVE` 只迁移附属明确修改的世界内容，继续使用创建时的边界、入口和出生
点。若新版本确实改变这些几何语义，可显式选择
`ADOPT_CURRENT_REGISTRATION`；本体只会在回调成功后原子替换存档快照，失败时仍保留
旧快照。采用该策略前，迁移必须先处理新增/移除区域中的方块、Portal 和实体。

旧 `StardewFarmSelectionOptions` 仅作为兼容 facade 保留：它是客户端展示项，
不能由本体持久化或权威校验。新布局不得再用它承载创建配置。

## 农场生命周期、初始化与附属状态

农场注册表的创建、所有权转移和删除提供有序观察者。回调只接收不可变快照，不暴露可变的 `FarmInstance`：

```java
StardewFarmPersistentData.Key FARM_STATE =
    StardewFarmPersistentData.register(
        ResourceLocation.fromNamespaceAndPath("myaddon", "farm_state"),
        2
    );

StardewFarmLifecycle.register(
    ResourceLocation.fromNamespaceAndPath("myaddon", "farm_lifecycle"),
    100,
    new StardewFarmLifecycleListener() {
        @Override
        public void afterCreate(StardewFarmLifecycle.FarmContext context) {
            if (context.server() == null) return;
            CompoundTag state = new CompoundTag();
            state.putString("bundle_variant", "hard");
            StardewFarmPersistentData.write(
                context.server(), context.farm().ownerUuid(), FARM_STATE, state);
        }

        @Override
        public void afterTransfer(StardewFarmLifecycle.TransferResult result) {
            // result.source() 和 result.transferred() 都是事务完成时的只读快照。
        }
    }
);
```

Listener 按优先级从高到低、同优先级按完整 ID 排序。`before*` 只会在核心前置条件通过后触发，`after*` 只会在注册表事务和脏标记完成后触发；“重复创建返回已有农场”、失败的转移和不存在的删除不会发出事件。Listener 是观察者，不能否决事务。单个 Listener 抛出异常会记录注册 ID 和阶段，然后继续核心事务与其他 Listener，避免一个附属破坏整个注册表。

需要在农场地形上放置附属内容时，注册版本化初始化步骤：

```java
StardewFarmInitializationSteps.register(
    ResourceLocation.fromNamespaceAndPath("myaddon", "grandpa_shed"),
    3,
    100,
    StardewFarmInitializationSteps.FailurePolicy.CONTINUE,
    context -> {
        // 使用 context.level() 和 context.farm() 幂等地检查/放置附属内容。
    }
);
```

步骤 ID 与版本共同构成幂等键。执行成功后版本写入农场存档；相同或更低版本不会再运行，提高版本会运行一次升级逻辑。异常步骤不会记录为完成，`CONTINUE` 会继续低优先级步骤，`STOP` 会停止本轮但不回滚此前成功的步骤。本体农场首次初始化完成后和玩家登录旧农场时都会运行待办步骤；外部依赖恢复后也可以显式调用 `StardewFarmInitializationSteps.runPending(level, ownerUuid)`。

本体地形初始化与附属步骤采用分离事务：附属失败不会把已完成的本体农场标回“未初始化”，也不会误删已经成功的其他步骤。附属自己的步骤仍应检查目标方块或实体是否已经存在，避免异常发生在部分世界修改之后时重复放置。

`StardewFarmPersistentData` 与动物状态采用同样的不可伪造 Key、显式 schema 版本和防御性 NBT 副本。所有权转移会保留整份命名空间数据和初始化完成版本；附属暂时缺席时，未知合法条目仍会跨读档和再次保存原样保留。删除农场会随实例整体删除这些状态，`beforeDelete` 可用于清理附属保存在其它 SavedData 中的外部索引。
`farmPersistentData.diagnostics()` 或
`StardewFarmPersistentData.diagnostics(server, ownerUuid)` 可以只读识别 orphan、
损坏和版本不一致条目，不会触发迁移或标脏存档。

选择页的额外布尔项通过 `StardewFarmSelectionOptions` 注册：

```java
StardewFarmSelectionOptions.register(
    ResourceLocation.fromNamespaceAndPath("myaddon", "hard_bundles"),
    100,
    Component.translatable("gui.myaddon.hard_bundles"),
    Component.translatable("gui.myaddon.hard_bundles.tooltip"),
    false,
    selection -> PacketDistributor.sendToServer(
        new MyBundleDifficultyPayload(selection.selected()))
);
```

本体只负责稳定排序、绘制、保留重建界面前的选择值，以及在进入玩家资料页前调用 Handler；不把 `Screen`、控件坐标或 `EditBox` 暴露给附属。选项本身是客户端只读展示，不参与核心创建判定，也不会自动写入农场存档。需要影响游戏规则时，附属必须用自己的 payload 在服务端验证并暂存，再在 `afterCreate` 中写入自己的 `StardewFarmPersistentData`，不需要注入 `FarmSelectionScreen.init/sendSelection`。

洞穴日结可以整体追加/接管，也可以只扩展果蝠水果池：

```java
StardewFarmCaveDailyHandlers.register(
    ResourceLocation.fromNamespaceAndPath("myaddon", "custom_cave"),
    200,
    context -> usesCustomCave(context.farm().ownerUuid())
        ? runCustomCave(context)
        : StardewFarmCaveDailyHandlers.Result.PASS
);

StardewFarmCaveDailyHandlers.registerFruitProvider(
    ResourceLocation.fromNamespaceAndPath("myaddon", "orchard_fruit"),
    100,
    () -> List.of(MyBlocks.CUSTOM_FRUIT.get()),
    context -> context.random().nextInt(8) == 0
        ? MyBlocks.CUSTOM_FRUIT.get()
        : context.currentFruit()
);
```

Handler 对已放置洞穴的活跃农场执行；即使本体 `caveChoice=none` 也会调用，方便附属用命名空间状态表达额外变体。返回 `SKIP_DEFAULT` 会停止后续 Handler 和本体果蝠/蘑菇流程。Fruit Provider 按顺序组合，返回 `null` 表示不改当前结果；其 `managedFruitBlocks` 会在农场离开果蝠模式时进入清理集合，替代对 `clearCaveFruits` 的尾部注入。

普通农场日常维护使用：

```java
StardewFarmDailyTasks.register(
    ResourceLocation.fromNamespaceAndPath("myaddon", "farm_foraging"),
    100,
    context -> updateAddonForage(
        context.level(), context.farm(), context.absoluteDay())
);
```

任务在本体作物、树、动物、采集和洞穴日结之后，对每个有在线成员且已初始化的农场执行一次。任务按优先级和完整 ID 稳定排序；单项异常不会阻止其它附属任务或玩家日结。任务可能在服务端主线程修改世界，但必须自行保持幂等，并用 `StardewFarmPersistentData` 保存需要跨日的状态。

需要替换本体随机农场碎片 pass 选出的幼树或碎片方块时，使用 `StardewFarmDebrisPlacements`：

```java
StardewFarmDebrisPlacements.register(
    ResourceLocation.fromNamespaceAndPath("myaddon", "wild_tree_species"),
    100,
    context -> context.stage() == StardewFarmDebrisPlacements.Stage.YOUNG_TREE
        ? chooseAddonSapling(context)
        : context.proposedState()
);
```

Provider 只替换“随机生成新碎片”的候选状态，不接管从既有碎片向相邻格扩散的算法。返回 `null` 或原状态表示不改；幼树结果仍经过本体生存检查。旧 `FarmDebrisDailyService.spawnRandomDebris` 方法以及两个 `ServerLevel.setBlock` 调用继续保留，尚未迁移的 redirect 仍可命中。

## 机器运行时 resolver 与 JEI 描述

本体数据包中的 `artisan` 配方继续负责可声明的输入、耗时、固定/复制/烟熏/种子机输出和品质规则。需要 Java 行为的特殊流程通过同一组有序 resolver 接入：

```java
StardewArtisanResolvers.registerCaskAgingRate(
    id("myaddon_wines"),
    100,
    input -> isMyQualityWine(input) ? 1.0F : null
);

StardewArtisanResolvers.registerSmokedOutput(
    id("myaddon_smoked_fish"),
    100,
    input -> smokedVariant(input).orElse(ItemStack.EMPTY)
);

StardewArtisanResolvers.registerSeedMakerOutput(
    id("myaddon_seed_map"),
    100,
    item -> {
        if (isBannedProduce(item)) return StardewArtisanResolvers.SeedResult.deny();
        Item seeds = customSeeds(item);
        return seeds == null
            ? StardewArtisanResolvers.SeedResult.pass()
            : StardewArtisanResolvers.SeedResult.output(seeds);
    }
);
```

Resolver 按优先级从高到低、同优先级按完整注册 ID 排序，异常会记录 ID 和输入后继续。酒桶 resolver 只在本体固定倍率表未命中时执行，并拒绝非正数、NaN 和无穷倍率。烟熏 resolver 在本体命名空间约定未命中时执行，输入和输出都使用防御性副本。种子机先执行附属链，`PASS` 回退本体特殊映射和 `<produce>_seeds` 约定，`OUTPUT` 指定结果，`DENY` 明确禁止。

烟熏与种子机的 JEI 构建现在调用同一运行时 resolver，因此附属不再需要分别注入 `FishSmokerBlockEntity`、`SeedMakerOutputResolver` 和 `ArtisanJeiRecipeFactory`。旧私有方法和既有 mixin 目标签名仍保留，迁移可以分版本完成。

附属自己注册了机器物品，并希望复用本体 artisan 数据与 JEI 类别时，在 Mod 构造阶段登记描述：

```java
StardewMachineTypes.register(
    id("fermenter_registration"),
    new StardewMachineType(
        id("fermenter"),
        id("fermenter"),
        "jei.myaddon.fermenter",
        StardewMachineType.Layout.AUXILIARY_INPUT,
        true,
        List.of(new StardewMachineType.AuxiliaryInput(
            ResourceLocation.withDefaultNamespace("sugar"), 1))
    )
);
```

机器类型会在 JEI 首次注册类别时冻结，晚注册会明确报错。它不会注册 Minecraft 方块、物品或 Block Entity，也不会强制附属继承本体机器；这些对象仍由附属负责。机器 ID 对应 `artisan` 配方中的 machine ID。当前稳定布局最多支持一个辅助输入，多槽位机器应由附属提供自己的菜单和 JEI 类别，不会被悄悄挤进错误布局。

无法由 artisan 定义推导的展示页可以通过防御性 DTO 追加：

```java
StardewMachineRecipeDisplays.register(
    id("fermenter_displays"),
    100,
    machineId -> machineId.equals(id("fermenter"))
        ? List.of(new StardewMachineRecipeDisplay(
            id("fermenter/apple"),
            machineId,
            List.of(new StardewMachineRecipeDisplay.Input(
                List.of(new ItemStack(MyItems.APPLE.get())), 1, false)),
            List.of(new StardewMachineRecipeDisplay.Output(
                List.of(new ItemStack(MyItems.CIDER.get())), 1, 1, 1.0)),
            120, false, -1))
        : List.of()
);
```

Provider 只描述 JEI，不会创建服务端配方或绕过机器验证。若附属的 Block Entity 继承 `TimedProductionBlockEntity`，它现在也实现 `StardewTimedProduction`，可只读查询输入、输出、完成时间、剩余分钟和 ready 状态；返回的堆栈不能修改机器内部库存。

在机器真正消耗主输入或辅助燃料前，可以有序修改产物和耗时，或拒绝本次生产：

```java
StardewProductionPlans.register(id("apple_preserves"), 100,
    (context, proposed) -> {
        if (!context.machineId().equals(
                    ResourceLocation.parse("stardewcraft:preserves_jar"))
                || !context.input().is(Items.APPLE)) {
            return Optional.of(proposed);
        }
        return Optional.of(new StardewProductionPlan(
            proposed.output(),
            Math.max(1, proposed.minutes() / 2)));
    });
```

Provider 按优先级和注册 ID 确定顺序，后项接收前项产出的计划；`Optional.empty()`
明确拒绝生产，异常或错误的 `null` 只隔离当前 Provider。上下文包含机器类型、
维度、位置、输入副本、可选玩家和 `automation` 标记，产物始终防御性复制。
Provider 必须同步且无副作用，因为自动化可能先模拟再实际插入，多次解析必须得到
一致结果。当前本体已把啤酒桶、腌菜罐、奶酪机、蛋黄酱机、榨油机、脱水机、
织布机、种子机、诱饵机、骨磨机、回收机、晶球破碎机、木炭窑、熔炉、重型熔炉
和熏鱼机等 16 种机器的手动/自动化实际提交入口接入该边界，并保证拒绝时不消耗
输入或煤；随机产物机器的模拟阶段不会为了预览而提前消耗随机数。晶球复制机、
孵化器、蜂房、避雷针和树液采集器等持续/环境型机器保留各自语义，后续使用专门
适配而不是伪装成一次性输入配方。

任务、统计、成就或联动系统可以观察已经提交的生命周期转换：

```java
StardewProductionEvents.register(id("machine_stats"), 100,
    event -> {
        if (event.phase() == StardewProductionPhase.COLLECTED) {
            recordAddonStatistic(
                event.machineId(), event.output());
        }
    });
```

事件按优先级和注册 ID 稳定派发，单个 Listener 异常不会阻止生产或后续 Listener。
事件只携带服务端维度、位置、机器 ID、输入/产物副本和完成时间，不暴露本体具体
Block Entity。共同基类会在计划提交和首次 ready 转换时发出 `STARTED/READY`；
上述 16 种已迁移机器在玩家或自动化取走最后产物前发出 `COLLECTED`。事件是已发生
事实的观察入口，不可拒绝；需要拒绝或改写生产应使用生产计划 Provider。

一次性输入不是所有机器共有的语义。晶球复制机保留模板并自动开始下一轮，蜂房和
虫饵盒按内部日程生产，避雷针依赖世界事件。附属需要跨这些形态组合规则时使用通用
机器周期层：

```java
StardewMachineCycles.registerPlan(id("faster_repeaters"), 100,
    (context, proposed) -> {
        if (context.kind() != StardewMachineCycleKind.REPEATING
                || !context.input().is(Items.DIAMOND)) {
            return Optional.of(proposed);
        }
        return Optional.of(new StardewProductionPlan(
            proposed.output(), Math.max(1, proposed.minutes() / 2)));
    });

StardewMachineCycles.registerListener(id("all_machine_stats"), 100,
    event -> recordCycle(event.kind(), event.phase(), event.machineId()));
```

`StardewMachineCycleKind` 明确区分：

| 类型 | 语义 |
| --- | --- |
| `BATCH` | 消耗有限输入，领取后停止 |
| `REPEATING` | 保留模板/催化剂，领取后自动开始下一轮 |
| `PASSIVE` | 无玩家输入，按内部日程生产 |
| `ENVIRONMENTAL` | 由天气、世界事件或外部环境触发 |

原 `StardewProductionPlans` 继续是批次机器兼容入口；本体共同基类先执行旧链，再把
结果交给 `BATCH` 周期链，因此已有附属行为和优先级不变。当前真实消费者包括：

- 晶球复制机使用 `REPEATING`：首次放入、自动化模拟/提交、领取和下一轮共用规则；
- 虫饵盒使用 `PASSIVE`：随机产物只在实际开始时生成，拒绝后按天退避，不会每 tick
  重掷随机数或反复调用附属；
- 避雷针使用 `ENVIRONMENTAL`：闪电触发在提交充能前解析计划，拒绝不会生成电池。

三者都发出 `STARTED/READY/COLLECTED`，旧配方、计时与存档字段不变。通用 Context
允许空输入，供 `PASSIVE/ENVIRONMENTAL` 使用，并保留玩家可选值及 `automation`
来源。蜂房的口味在领取时依据当时附近花朵计算，太阳能板会暂停倒计时；它们需要
完成阶段产物解析与可暂停周期语义，暂不为了表面统一而固化成错误的开始阶段产物。

附属不必继承本体 `TimedProductionBlockEntity`。拥有自己方块实体的机器在扣物或
提交环境触发前调用 `StardewMachineCycles.resolve(context, proposed)`；提交状态后
用 `announce(event)` 上报事实。Context、Plan 和 Event 的物品均防御性复制，
Listener 异常隔离，两个扩展点也会出现在
`/stardew debug extensions explain stardewcraft:machine/cycle_plan|cycle_event`
中。`StardewTimedProduction` 新增的默认查询可报告周期类型和是否由自动化启动，
旧附属实现无需修改。

取消尚未被伪装成一个会吞物的布尔操作：批次输入、重复模板、辅助燃料和环境触发
需要不同退款策略。后续取消协议会在周期类型上声明返回物、不可退成本与中断原因；
在这之前，附属不应通过反射清空本体 Block Entity。

## 果树、野树与树液采集器运行时

`StardewTreeData` 仍用于数据驱动的树木元数据；当附属拥有自己的多方块结构、成长存档或树液规则时，再注册运行时类型和适配器：

```java
ResourceLocation treeId = id("pear_tree");
StardewTreeTypes.register(
    new StardewTreeType(
        treeId,
        StardewTreeType.Kind.FRUIT,
        "block.myaddon.pear_tree",
        28,
        5,
        false
    ),
    100,
    new StardewTreeRuntimeAdapter() {
        @Override
        public StardewTreeState inspect(LevelReader level, BlockPos pos) {
            PearTreePart part = findPearTreePart(level, pos);
            if (part == null) return null;
            return new StardewTreeState(
                treeId,
                part.root(),
                part.isSapling()
                    ? StardewTreeState.Part.SAPLING
                    : StardewTreeState.Part.TRUNK,
                part.visualStage(),
                part.isMature(),
                part.tapperSupports()
            );
        }

        @Override
        public boolean growOneDay(ServerLevel level, StardewTreeState tree) {
            return PearTreeGrowth.get(level).growOneDay(level, tree.root());
        }

        @Override
        public FertilizerResult fertilize(
                ServerLevel level, StardewTreeState tree) {
            return PearTreeGrowth.get(level).fertilize(level, tree.root())
                ? FertilizerResult.APPLIED
                : FertilizerResult.ALREADY_APPLIED;
        }

        @Override
        public TapperCycle resolveTapperCycle(
                ServerLevel level,
                StardewTreeState tree,
                BlockPos support) {
            return new TapperCycle(new ItemStack(MyItems.PEAR_RESIN.get()), 5);
        }
    }
);
```

适配器不要求继承本体 `FruitTreeBlock`、`WildTreeSaplingBlock` 或使用固定高度。`inspect` 必须只读、客户端安全，并从任意属于该树的方块返回同一个不可变根坐标；`tapperSupports` 是允许安装采集器的完整支撑方块集合。本体先识别自己的树，再按优先级和完整类型 ID 调用附属适配器，因此附属不能意外接管核心树种。返回的类型 ID、成长阶段和根位置都会验证；单个适配器异常只记录该类型并回退。

`StardewTreeRuntime.inspect` 为客户端成长阶段、Jade 或自定义界面提供与方块结构无关的只读 DTO。`growOneDay` 和 `fertilize` 会重新识别并验证当前根，避免调用者用过期状态修改另一棵树。适配器负责自身的每日索引和存档；本体不会扫描全部世界替附属维护位置集合。

核心流程已经接入：

- 果树间距检查把已注册的附属树视为树木；
- `/growtrees` 对每个 `(typeId, root)` 每次只推进一次，并继续要求创造模式和 2 级权限；
- 树肥由适配器返回 `PASS/APPLIED/ALREADY_APPLIED/MATURE/CANNOT_APPLY`，物品消耗、声音、粒子和消息仍由本体完成；
- Tapper 按适配器给出的整棵树支撑集合统计最多 4 个采集器，服务端启动周期时再次验证树根并复制产物堆栈。

为了让现有附属分批迁移，`FruitTreeRules.isTreeAt`、`GrowTreesPayload.handle`、`TreeFertilizerItem.useOn`、`WildTrees.findTapperSupportDef/findTapperTreeRoot`、`TapperBlock.countTappersOnTree` 和 `TapperBlockEntity.startCycleIfEmpty(String)` 的原描述符都继续保留。附属可以先迁移果树识别，再迁移树肥或 Tapper，不要求一次删除全部 mixin。

## 社区中心只读进度与服务端 Action

附属查询玩家社区中心状态时使用深拷贝快照，不需要访问 `CommunityCenterSavedData.PlayerProgress` 的私有 Map：

```java
StardewCommunityCenterProgress.Snapshot progress =
    StardewCommunityCenterProgress.snapshot(serverLevel, playerUuid);

for (StardewCommunityCenterProgress.BundleProgress bundle : progress.bundles()) {
    int filled = bundle.filledSlots();
    boolean rewardReady = bundle.rewardAvailable();
}
```

`bundles`、每个 bundle 的 `slots` 和 `areasComplete` 都是不可变副本；后续日结、捐赠或领奖不会反向改变已取得的快照。快照会同时包含当前定义里的 bundle 与存档中暂时没有定义的旧 bundle ID，避免卸载附属后观察工具把未知进度静默藏掉。

附属自己的 C2S payload 不应直接调用可变存档方法，而应转入服务端 Action：

```java
StardewCommunityCenterActions.Result result =
    StardewCommunityCenterActions.deposit(player, bundleId, ingredientSlot);

StardewCommunityCenterActions.purchaseVault(player, bundleId);
StardewCommunityCenterActions.partialDeposit(
    player, bundleId, ingredientSlot, requestedAmount);
StardewCommunityCenterActions.claimReward(player, bundleId);
```

这些入口每次都会重新检查当前菜单、只读模式、光标权威堆栈、bundle/区域、槽位、品质、数量、玩家金钱和奖励可领状态；成功后由本体广播菜单变化并同步完整进度。核心四种网络 payload 也已转发到同一 Action，因此附属调用与本体客户端不会产生两套判定。`BundleMenu.tryDeposit/tryPurchaseVault/handlePartialDeposit` 和 `BundleClaimRewardPayload.handle` 的原签名继续保留。

Bundle ingredient 或奖励解析现在直接接受 `namespace:path`，例如 `minecraft:apple` 或附属物品 ID；无效命名空间返回空堆栈。旧数字 SDV ID、`BO_`/`R_` 前缀与本体路径回退保持不变。

玩家级 bundle 难度或完整变体使用有序 catalog Provider：

```java
StardewCommunityCenterVariants.register(
    id("bundle_difficulty"),
    100,
    (context, current) -> isHardFor(context.playerId())
        ? current.withVariant(
            id("hard"),
            buildHardDefinitions(current.definitions()))
        : null
);
```

`StardewBundleDefinition` 与 `StardewBundleIngredient` 是稳定、不可变且与现有网络字段一一对应的 DTO。Provider 接收前序 Provider 已验证的 catalog，可替换、追加或调整 bundle；返回 `null` 表示不改。候选必须非空、bundle ID 唯一，且每个 DTO 会验证槽位、数量、品质和 required count。异常只拒绝该 Provider 的候选并保留上一 catalog。

服务端菜单、槽位长度、完成判定、区域判断、奖励菜单和完整同步都按玩家解析同一 catalog；客户端仍接收原来的 `BundleDefinition` 编码，所以没有修改协议号或 wire format。`variantIds` 是服务端可观察的选择结果，不复用旧网络字段。附属可以把自己的标准/困难目录转换为该 DTO，再逐步删除围绕 `BundleDataManager` 的线程局部上下文 mixin。
底层 bundle 定义、区域索引、区域名称和显示键由同一个不可变 revision 一次发布；
数据包 reload 与客户端网络同步共用该发布边界，读取端不会观察到新 bundle 配旧区域
索引的中间状态。该改动没有改变 bundle ID、数据格式或现有网络字段。

附属的选择状态和其它社区中心数据使用版本化命名空间存储：

```java
StardewCommunityCenterPersistentData.Key difficulty =
    StardewCommunityCenterPersistentData.register(id("difficulty"), 1);

CompoundTag payload = new CompoundTag();
payload.putBoolean("hard", true);
StardewCommunityCenterPersistentData.write(
    serverLevel, playerUuid, difficulty, payload);
```

读取返回保存时版本和防御性 NBT 副本；修改源标签或读取结果不会改变存档。未知命名空间条目在附属未安装时仍随 `CommunityCenterSavedData` 原样加载和保存，核心 debug reset 不会擅自删除它。
`StardewCommunityCenterPersistentData.diagnostics(level, playerUuid)` 会对该玩家的
完整附属状态做只读分类；它不会为了生成报告创建、删除或修改任何条目。

奖励解析器同时用于按钮领奖、奖励抓取菜单和区域完成时的自动发放：

```java
StardewCommunityCenterRewards.register(
    id("custom_reward"),
    100,
    context -> context.rewardDescriptor().equals("myaddon:starter")
        ? new ItemStack(MyItems.STARTER_KIT.get())
        : null
);
```

Resolver 按优先级和完整 ID 组合，每次接收当前候选的防御性副本；返回 `null` 表示不改，返回空堆栈可明确取消物品奖励。异常会记录 resolver 与 bundle ID，并继续后续解析。

装备元数据覆盖防御、免疫、攻击、暴击、磁力、幸运、发光、效果列表和武器数值。槽位先读取 `StardewEquipmentDataApi` 的 `slot`，再回退本体类型。玩家装备槽保存和同步完整 `ItemStack`，因此附属的 Data Component 不会被降级成物品 ID；旧字符串装备存档在读取时自动迁移。

武器的 `primary_skill` / `secondary_skill` 由附属注册：

```java
StardewWeaponSkillHandlers.register(MY_SKILL_ID, context ->
    InteractionResultHolder.success(context.weapon())
);
```

客户端的技能键可以从任意手持物品的公共装备数据读取技能 ID，但服务端会再次从当前完整手持栈解析并调用 Handler。未注册技能、Handler 返回 `PASS` 或旧本体武器会回退现有 `IStardewWeapon` 行为；公共技能不会自动替换 Minecraft 物品原生右键逻辑。

### 服务端战斗事件（实验）

附属可以在不注入本体怪物、玩家伤害处理器或具体武器类的情况下组合服务端伤害：

```java
StardewCombatEvents.registerDamageModifier(
    ResourceLocation.fromNamespaceAndPath("myaddon", "blessed_weapon"),
    100,
    context -> isBlessed(context.attacker())
        ? StardewCombatDamageDecision.set(context.amount() * 1.25F)
        : StardewCombatDamageDecision.pass()
);
```

Damage modifier 按优先级从高到低、平级按完整注册 ID 稳定执行。每个 modifier
接收上一个结果形成的当前伤害值，可返回：

- `pass()`：不改变当前值；
- `set(amount)`：给后续 modifier 一个新的非负有限值；
- `deny()`：立即把本次伤害归零并停止后续 modifier。

单个 modifier 抛出运行时异常时只记录其注册 ID，并继续执行后续 modifier。注册表
为空时直接返回 NeoForge 提供的原伤害值，因此旧武器、旧怪物和没有附属的世界行为
不变。该入口只在逻辑服务端执行，不能作为客户端自行判定伤害的依据。

确认死亡且伤害归属于服务端玩家后，还会发送只读的击杀通知：

```java
StardewCombatEvents.registerKillListener(
    ResourceLocation.fromNamespaceAndPath("myaddon", "slayer_progress"),
    100,
    context -> recordKill(
        context.player(),
        context.targetType(),
        context.targetTags(),
        context.dimension())
);
```

通知携带玩家、目标实体和类型、目标 tag 快照、伤害来源、维度与死亡位置。listener
同样稳定排序并隔离异常；它是观察事件，不授予客户端权限，也不替代附属自己的
幂等奖励或持久状态。伤害和击杀入口目前列入 experimental 清单，后续可在保持
这些组合语义的前提下继续增加武器、技能、效果与奖励上下文。

## 精通与职业

精通奖励路径：

```text
data/<namespace>/mastery_rewards/*.json
```

一份定义绑定一个现有核心技能，可按 `priority` 追加 `item`、`recipe`、`stat` 或仅展示的 `placeholder` 行。五系本体奖励已迁入该格式，服务端奖励表与客户端精通界面共用登录同步快照。
规范定义、按技能和优先级生成的运行时奖励行、客户端同步 JSON 属于同一个 revision；
无效 reload 或同步候选会整批拒绝并保留上一版。

职业元数据路径：

```text
data/<namespace>/professions/*.json
```

本体 30 个职业的数据包含所属技能、5/10 级、父职业、名称/描述键和可选 `effect_handler`。附属可注册 Handler，并通过数据覆盖把现有职业绑定到它：

```java
StardewProfessionEffectHandlers.register(MY_HANDLER_ID, context -> {
    if (StardewProfessionEffectHandlers.SELL_PRICE_MULTIPLIER.equals(context.operation())) {
        return context.value() * 1.02;
    }
    return context.value();
});
```

当前公开的真实操作是 `SELL_PRICE_MULTIPLIER`。职业拥有状态仍保存旧 `0..29` 数字，因此外部命名空间职业定义可被读取，但不会凭定义自动成为升级界面的第 31 个可选职业。
职业规范定义、运行时查询和客户端同步 JSON 共享同一个 revision；无效 reload 或同步
候选会保留上一版，不改变已有职业编号或效果调用。

## 本体数据迁移

本体静态商店现在位于 `data/stardewcraft/shops/*.json`，用 `legacy_id` 兼容 `SeedShop`、`Blacksmith` 等旧调用和库存存档键。旅行货车、书商每日随机货物等依赖玩家/日期的算法仍是动态 Provider 或运行时逻辑，静态基础商店不再由 Java `REGISTRY.put` 构造。

16 条本体特殊订单位于 `data/stardewcraft/special_orders/*.json`。`legacy_id` 保留旧任务状态里的 `Willy`、`Demetrius2` 等 ID；目标、奖励、随机模板和结束清理字段均由 reload 表加载。

## 跨系统内容引用目录

地图、世界锚点、节日地图覆盖、NPC、商店、任务、剧情、进度、农业、生产和战利品等领域会被投影到统一的只读内容目录。它不替代各领域的数据包 Loader、Java 注册入口或存档；旧系统仍是定义和运行时行为的唯一权威。目录只在查询时读取当前原子快照，再执行第二遍引用解析，因此 reload 后已经删除的目标不会被旧缓存伪装成有效。

核心内置类型在 `StardewContentTypes`，引用语义在 `StardewContentReferenceRoles`。附属可以发布自己的领域类型，也可以引用核心或其它附属节点：

```java
ResourceLocation featureType = id("content_type/orchard_feature");
ResourceLocation source = id("content/orchard_tasting");

StardewContents.register(source, 0, () -> List.of(
    new StardewContentDefinition(
        new StardewContentKey(featureType, id("orchard_tasting")),
        source,
        List.of(
            StardewContentReference.required(
                StardewContentReferenceRoles.LOCATION,
                new StardewContentKey(
                    StardewContentTypes.LOCATION,
                    ResourceLocation.fromNamespaceAndPath(
                        "stardewcraft", "town"))),
            StardewContentReference.required(
                StardewContentReferenceRoles.PRODUCT_ITEM,
                new StardewContentKey(
                    StardewContentTypes.ITEM,
                        ResourceLocation.fromNamespaceAndPath(
                            "minecraft", "apple"))))));
```

内容改名时使用独立 alias Provider，不要复制一份旧定义，也不要在每个消费系统
分别维护兼容表。alias 与目标必须属于同一内容类型；重复 alias、覆盖真实定义、
缺失目标和循环引用都会成为结构化目录错误。Provider 注册在初始化阶段冻结，但
每次目录失效时都会重新读取其当前返回值，因此可以安全投影 reload 后的领域快照：

```java
StardewContentKey canonical =
    new StardewContentKey(featureType, id("orchard_tasting"));
StardewContentKey legacy =
    new StardewContentKey(featureType, id("legacy_orchard_tasting"));

StardewContents.registerAliases(
    id("content/orchard_aliases"),
    0,
    () -> List.of(new StardewContentAlias(legacy, canonical)));

StardewContentKey resolved =
    StardewContents.resolve(legacy).orElseThrow();
```

alias 可以形成有界链，最终必须落到真实内容节点。`StardewContents.find(legacy)`
会返回规范节点；引用快照仍保留声明时的旧 ID，便于定位需要迁移的源文件。
`StardewContents.aliases()` 提供来源、直接目标、最终规范目标和错误列表。alias
只影响目录查找和依赖诊断，不替代领域自己的存档迁移或运行时解析。单次目录最多
接受 4096 个 alias，单条链最多 256 层，超过上限会形成目录错误。

Provider 只声明来源与引用，不能自己声称目标已经解析；`resolved` 始终由核心根据本次目录计算。Provider 按优先级稳定执行并隔离异常，但相同 `StardewContentKey` 只有第一个所有者生效：内置投影先加入，所以诊断 Provider 不能覆盖真实的地图、节日、NPC、商店或任务定义。

可扩展的 Condition、Action、Item Query 和 Quest Objective 若在自己的强类型 payload 中保存内容 ID，可以使用新增的四参数注册重载。第四个参数接收所属内容节点与同一份已解码 DTO，不需要反射或公开 DTO 内部字段：

```java
StardewActions.register(
    id("spend_orchard_marks"),
    Codec.intRange(1, 100),
    (context, amount) -> spend(context.player(), amount),
    (owner, amount) -> List.of(
        StardewContentReference.required(
            StardewContentReferenceRoles.CURRENCY,
            new StardewContentKey(
                StardewContentTypes.CURRENCY,
                id("orchard_marks")))));
```

同样的第四参数可用于 `StardewConditions.register(...)`、`StardewItemQueries.register(...)` 和 `StardewQuestObjectives.register(...)`。旧三参数重载保持原样；没有引用的类型无需提供空 Provider。返回集合会被防御性复制，异常或 `null` 会成为所属节点的结构化 issue，不会中断其它定义。`owner.id().getNamespace()` 可用于让附属 payload 中的裸 ID 相对其内容所有者解析，而不是错误落入本体命名空间。

```java
StardewContentCatalogSnapshot catalog = StardewContents.snapshot();
List<StardewContentNodeSnapshot> broken = catalog.unhealthyNodes();
List<StardewContentReferenceSnapshot> dangling =
    catalog.unresolvedReferences();
```

必需引用缺失或节点携带领域问题时，节点为不健康；可选引用缺失仍可见，但不会单独使节点失败。当前核心投影会检查：

- 地点父级、逻辑区域所属地点、锚点所属地点、节日地点/地图覆盖/商店和地图覆盖锚点；
- 数据 Portal 的定义身份、Forage 区域的可选同 ID 逻辑区域与生成方块、矿井主题的全部地形和矿石方块；
- NPC 商店、商店所有者/动态库存 Provider/商品与交换物品；
- 任务的 `next_quests`，邮件附件/任务/特殊订单/所学配方；
- 五项核心技能、职业的技能/父职业/可选效果 Handler、精通奖励的技能/物品/配方，以及解锁来源中的配方；
- 秘密纸条揭示的 NPC 和遗失藏书中的嵌套 Condition；
- 过场事件的结构化触发地点/NPC，友情、物品、邮件、秘密纸条和事件历史前置条件，以及内置命令明确声明的 NPC、物品、方块、实体、任务、邮件、配方和解锁来源；`question`/`simultaneous` 会递归检查；
- 附属过场触发器和命令可用强类型引用 Provider 声明自己的依赖；未知命令字段和任意文本不会被猜测成内容引用；
- 日常委托池的交付/资源/怪物目标 NPC，以及四季交付物、鱼类和资源物品；
- 钓鱼池的确定/随机渔获与可识别逻辑地点，鱼塘的精确鱼种/产物/扩容物品；
- 博物馆奖励的指定捐赠物与 Action，以及公会杀怪目标的奖励 Action；
- 矿井怪物 Profile 的实体类型，公会目标与日常委托怪物标签到 Profile 的连接；
- 矿井怪物刷怪表的精确/同 mechanic 主题与所有候选 Profile；
- NPC 礼物喜好 patch 的目标 NPC、增删物品，以及合成后每个 NPC 的有效礼物物品；
- 遗物点有效掉落组的可识别逻辑地点和确定物品，以及运行时掉落 Provider 主动声明的静态引用；
- 特殊订单委托人、送达目标、奖励邮件和结束清理内容；
- 建筑材料/结果物品、农场布局及其复合身份挂点；
- 本体与附属作物类型的识别方块/种子/产物、树木类型，以及动物类型的实体、产物、工具、替代类型和嵌套 Condition；
- 社区中心精确物品槽；
- 机器类型、工匠配方、制作配方与烹饪配方的精确输入/输出物品；
- 晶球掉落、奖券奖励、矿井宝箱、世界战利品和钓鱼宝箱中的条件及递归 Item Query 引用。

Minecraft 物品与方块使用不同的目录类型和原版注册表解析，不会把非物品方块伪装成物品。虚拟商品（如 `recipe:`、`wallpaper:` 和 `random:`）、物品标签、类别匹配及特殊订单随机占位符仍由其领域系统解释，不会被误报成缺失 Minecraft 物品。每个核心领域先在临时候选中完整投影，成功后才合并；一个领域的瞬时或附属错误不会留下半份节点，也不会阻断其它领域。NPC 等可独立枚举的领域还会按节点隔离：一个附属 NPC 的聚合数据不一致时，该 NPC 自身携带 `projection_failed` 诊断，其他 NPC 仍可被任务、商店和剧情引用。

服内可以先查看总览，再按类型和 ID 下钻：

```text
/stardew debug content
/stardew debug content stardewcraft:festival
/stardew debug content stardewcraft:festival stardewcraft:egg_festival
```

该 API 当前列入 experimental 清单；它只新增观察面，不修改数据包路径、网络协议、存档字段或既有注册方法。

每次服务端数据包 reload 完成并准备同步客户端内容时，核心会自动运行同一目录验证。报告是建议性的：各领域已经按自己的原子规则接受或拒绝候选，目录不会因为另一个附属暂时缺失而回滚全部内容。日志先输出汇总，再最多列出 50 个目录问题、50 个不健康节点和每节点 8 条缺失必需引用；完整结果始终可通过 API 或 debug 命令读取，避免大型整合包把日志无限刷屏。

## 可重载定义

`AtomicDefinitionStore<T>` 提供：

- 不可变 `DefinitionSnapshot<T>`；
- 单调递增版本；
- 基于规范来源文本的 SHA-256；
- `DefinitionDiagnostic` 错误与警告；
- 本地候选原子替换；
- 远端版本、哈希和内容一致性校验。

候选中只要存在一个 `ERROR`，活动快照就完全不变。定义 Loader 应先解析、收集全部诊断，再调用 `applyLocal`，不能边读边修改运行状态。

Minecraft 已经按数据包优先级解析同一路径资源，因此 Loader 接收的是胜出的完整定义。同一逻辑 ID 若从不同资源路径重复声明，应报错，而不是依赖遍历顺序决定胜者。
