### 4.5 预生成地图 manifest

首先尝试运行现有深度校验：

```bash
python3 scripts/replace_pregen_terrain.py --verify
```

该命令未进入资源扫描，因为本机缺少 `nbtlib`，且 `requirements-build.txt` 没有锁定该工具依赖。本轮不临时安装未固定版本，因此深度 NBT 调色板检查仍待补齐可复现环境。

随后使用系统工具独立核对 manifest 和打包资源，发现资源目录中存在 9 个未跟踪、未列入 manifest 的动态室内区域文件：

```text
r.47.38.mca  r.47.39.mca  r.47.40.mca
r.48.38.mca  r.48.39.mca  r.48.40.mca
r.49.38.mca  r.49.39.mca  r.49.40.mca
```

这些文件共约 17 MB，坐标落入安装器明确保护的 `rx >= 36 && rz >= 36` 区域，却已被本地 `processResources` 放入开发输出。它们未被删除，已移动到可恢复隔离目录：

```text
tmp/forge-port-baseline/quarantined-protected-regions-2026-09-20/
```

重新执行 `processResources` 后，独立校验结果：

- manifest version 17 与 `CURRENT_PREGEN_VERSION` 一致。
- 24 个 COPY 项的文件存在、大小和 SHA-256 全部一致。
- 129 个 DELETE 项格式有效。
- manifest 文件名无重复且均符合 region 命名格式。
- manifest 不包含受保护动态室内区域。
- 资源目录没有 manifest 之外的 region 文件。
- `build/resources/main` 不再残留上述 9 个受保护 region 文件。

### 4.6 模型纹理与方块图集

执行：

```bash
python3 scripts/check_model_atlas.py
```

首次检查发现蓝色花盆目录下有四个未跟踪的旧草稿模型：

```text
blue_flowerpot/spring.json
blue_flowerpot/summer.json
blue_flowerpot/fall.json
blue_flowerpot/winter.json
```

运行时代码实际注册的是 `blue_flowerpot/<season>/blue_flowerpot.json`。四个外层草稿不仅没有调用方，纹理路径还指向不存在的图片，其中秋季和冬季几何也早于当前嵌套模型。同批草稿还留下 6 张无模型引用的重复基础贴图和旧四季粒子贴图。以上 10 个文件均未删除，已移动到可恢复隔离目录：

```text
tmp/forge-port-baseline/quarantined-stale-blue-flowerpot-models-2026-09-20/
```

复查结果：

- 所有模型引用的纹理文件均存在。
- 所有模型纹理均已纳入 Minecraft 方块图集。
- 本轮 18 个新增/修改方块模型均直接绑定了粒子纹理，不依赖含糊的继承结果。
- 9 个相关 blockstate/item 模型文件中的 31 条模型引用全部能解析到现有模型。
- `processResources` 重新执行通过。

## 6. 用户实机验收边界

下列项目不能由编译、资源脚本或 GameTest 代替，建立正式迁移基线前需要明确标成“已验收”或“已知待办”：

1. 蓝色花盆在四季切换后的内容、朝向、物品形态和破坏粒子。
2. 熔炉、酒桶、罐头瓶、骨磨和重型熔炉是否存在静态模型与动态渲染重复、闪烁或内容物错位。
3. Town Door 在无 Sodium/Iris、仅 Sodium、Sodium+Iris 三组环境下的开合、裁剪和跨区块观察。
4. 建筑蓝图在单机与联机中的主手/副手消耗、农场许可归属和真实阻挡方块提示。
5. NPC 日程跨图移动、卡点恢复和重启后继续执行。
6. 各农场出生点、海滩淡水塘、可达地形及季节植被密度。
7. 温室及预生成地图在新存档、旧存档升级和完整重启后的结果。

这些结果属于 1.21.1 基线的行为证据；迁移到 Forge 后需要按同一观察项重新验收，而不是共享一次结论。

## 7. 建立迁移分支前的门槛

以下条件全部满足后，才能创建 `1.20.1-forge`：

1. 当前在研主题的目标和未决项明确。
2. `classes` 与 `checkTranslations` 继续通过。
3. 与当前改动有关的资源检查和定向 GameTest 通过。
4. GameTest 日志明确显示实际运行的必需测试数量，不能只看 Gradle 成功。
5. 需要客户端或重启验证的项目明确标注已完成或仍待用户验收。
6. 预生成地图 manifest 与 region 集合一致。
7. 获得提交授权并形成一个明确的基线提交。
8. 从该提交的干净检出重新执行基线验证。
